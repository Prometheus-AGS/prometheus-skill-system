# Two running KBD sessions on one machine

The operator works on one project in two terminals or coding harnesses. A can record a blocker, B can see and resolve it while A is still running, and A can see B’s resolution. Opening another session hours later and rereading old progress is useful recovery, but does not demonstrate live communication.

**Scope.** Full pack CLI, local KBD runtime, existing team handoff commands, their operator instructions, and the local integration runner. Reuse cand-001, cand-002 and cand-003 from the child analysis. Both sessions must use checkouts registered to the same project UUID and the intended local authority; include one case using the same checkout and one validating a second supported registration. The ordinary workflow requires neither a network account nor a running Companion. Journal progress is project-visible. The named recipient and explicit acceptance apply to task handoff.

## LOCAL-001 · Exchange an actionable update while both sessions are running

**Given** independent sessions A and B on this host, each already running the shipped KBD event reader against this project, **when** A records “Review is blocking release” under a fresh blocker ID, **then** B sees that message and its signed event ID without a manual refresh or restarting either reader. **When** B clears that same blocker with “Reviewed and ready”, **then** A sees the resolution while its original reader remains alive. A third fresh audit confirms both command IDs and exactly one committed effect per ID. Both readers must have consumed a known baseline marker before A sends the first message. Include a receipt with their distinct PIDs, different session labels, baseline event, write/read timestamps, project ID, event IDs and hashes. Use a configurable bounded deadline (30 seconds per observation on the local certification host), polling conditions rather than sleeping for success.

Run the exchange twice. First, the configured socket is absent and no Companion is launched in either session’s environment. Second, both sessions use one live headless Companion socket on this host with remote control selected. In the latter case independently correlate the requests and signed events at that socket. The same-host two-node replication case belongs to PEER-002. Interrupt one reader, commit work while it is stopped, and resume from its recorded event cursor. Assert that every expected event is applied once by the resumed consumer, including events sharing an observed revision when applicable. Document the resume interface and deduplication rule; preserve existing newline-delimited event output. A separate registered project must see neither update.

## LOCAL-002 · Report where a read came from and preserve authority on retries

**Given** valid local history and explicitly requested Companion control, **when** the endpoint disappears, **then** interactive status, audit and watch must identify local fallback and retain parseable stdout. Watch must continue to show local commits after a connection refusal, report return to the requested Companion source, and catch up after reconnect in the original watcher process. Prove remote resumption with an event unavailable in the fallback store, or capture a fresh read on the restored control socket carrying the exact signed event and correlate it to output from that same watcher PID. A permanently local watcher must fail this case. Assert ordered catch-up and no duplicate effect at the saved cursor. A caller requesting a receiver-only read must get failure when the selected receiver cannot be reached. The receiver’s own control API is an acceptable strict entry point. **When** a reachable endpoint denies access or rejects the project or returns an incompatible response, **then** a populated local cache must not turn that remote request into success. Test explicit denied and malformed/incompatible responses through real control configurations/production services, without mocking the client or authority; a real HTTP service serving a version-incompatible wire contract may be used solely as a negative protocol control. Treat ordinary local mode as distinct from explicit remote mode.

**Given** A and B act concurrently, **when** they contend for the same work claim, **then** the canonical result identifies the single active owner or the documented explicit conflict. Neither party can silently overwrite the other. On interrupted command submission, reconcile the original command ID and audit before retry; a pre-dispatch refusal and an ambiguous post-commit disconnect produce distinguishable results. Repeating an identical logical command yields one committed effect. Retain the signed audit, claim state, CLI exit codes, stdout and stderr.

## LOCAL-003 · Accept a handoff from a second active session

**Given** two active harness sessions using the same authoritative local team-state file, **when** A creates a handoff with a task, destination role/harness, expected task revision, next action and a real evidence reference, **then** ownership remains with A until B explicitly accepts. After acceptance, both sessions read B as owner with the same advanced revision. Repeating the unchanged acceptance must return the same accepted handoff and leave revision and ownership unchanged. A stale acceptance or a wrong recipient must fail without mutating the authoritative task. The reference must open to the expected artifact in B’s checkout. Copying a packet to an independent team state cannot transfer ownership on the original authority. Preserve permissions on role-private references.

## Release evidence

All three scenarios are local execution gates. The recorded fallback and watch failures and the prior lesson that projections can lag committed history require independent journal and checkout readback. The existing readback of revision 2577 is baseline evidence only. Execution must attach passing receipts for each positive and negative case. The verification contract specifies all gates and collaborators. No physical LAN or remote machine is required for this release claim.
