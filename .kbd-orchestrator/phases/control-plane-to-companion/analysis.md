## 2. Candidate evaluation

### 2.1 Discovery (gap 1, Q2) — verdict: adopt iroh's mDNS and Mainline DHT address lookups; reject libp2p-kad

iroh documents four discovery services (Tier 2, docs.iroh.computer/concepts/discovery): DNS (default), Pkarr, Local (mDNS), and DHT (Mainline). The DHT path publishes signed pkarr records to the BitTorrent Mainline DHT, which is a Kademlia DHT. After the 1.0 rename of "discovery" to "address lookup" these live in separate crates, named in the registry source of the version the pack actually resolves (`substrate/sovereign-sync/Cargo.lock`: iroh 1.0.3; `~/.cargo/registry/.../iroh-1.0.3/src/address_lookup.rs:47-51`): **`iroh-mdns-address-lookup`** and **`iroh-mainline-address-lookup`**. Per review, both are at 0.5.0 on crates.io (2026-08-18); analyze did not re-query. They are added with `Endpoint::builder(...).address_lookup(...)`, callable multiple times. Per review (crates.io dependency listings, not re-queried by analyze because the Tier 3 cap was reached), both 0.5.0 crates depend on `iroh ^1.0.0` and `iroh-base ^1.0.0`, so they build against the locked iroh 1.0.3; no bump above the pack's `iroh = "1.0.2"` security floor is needed for discovery, and the conditional regression run is withdrawn. Both crates live in `n0-computer/iroh-address-lookups`.

Exposure caveat the spec must weigh: Mainline lookup **publishes** each node's signed pkarr record (its relay URL and direct addresses, keyed by its public EndpointId) to the public BitTorrent DHT. Nothing in the record grants admission, but it does make the node's reachability information world-readable. For a pairing-gated, local-first product the recommended default is DHT publication **off**, enabled per operator when WAN lookup without the n0 relay is wanted; pkarr-relay lookup (already the n0 preset) and mDNS cover the common cases without publication. This is a plan-stage decision, and the Companion spec §25.2 row that justifies iroh with "no DHT gossip tax" must be amended to state the opt-in, since the analysis is now recommending a DHT the row was written to avoid.

This reframes Goal 3 without violating doctrine. The Companion spec §25.2 chose iroh over libp2p in part for "no DHT gossip tax", and HMA `references/sync/peer-crdt.md:80-85` makes "admission = device pairing, not open discovery" the rule. A DHT used only for **address lookup** (how to reach an EndpointId already trusted) leaves admission where both documents put it: Ed25519 pairing plus the allowlist `sovereign-sync::P2PIdentity::authorize_endpoint` already enforces. Membership stays iroh-gossip 0.101 (Tier 3: 585k downloads, updated 2026-06-15).

`libp2p-kad` is rejected on two grounds: the Companion spec's forbidden-dependency table (L183: "`libp2p` directly | Sovereign-sync already uses Iroh; the Companion consumes sovereign-sync") and the cost of a second transport stack beside iroh. HMA does not name libp2p in any rule; its only mentions are research notes under `docs/research/`.

Recommendation: `Endpoint::builder(presets::N0)` plus mDNS lookup (LAN) plus Mainline lookup (WAN, relay-independent), keeping the existing static `[peers].bootstrap` list as a third source. "Hand-maintained peer lists" in Goal 3 become optional, not removed.

### 2.2 Crate ownership and authority location (gaps 2, 7) — three options scored; operator amendment required before plan

The sovereign-sync path-dependency closure is kbd-runtime, storage-provider, learner-model, skill-index (dev: kbd-mobile), and `tools/prometheus-cli` depends on kbd-runtime by path. HMA's `compatibility/prometheus-control-plane.json` binds `lifecycle: prometheus`, `canonicalState: signed-loro-event-map`, projections read-only, minimum package 1.7.0. Goal 5 as written says "substrate crates are removed from the pack"; Goal 2 says the Companion "owns" the node providing "runtime authority". Revision 1 of this analysis narrowed both unilaterally; that was an error. The options, scored on five criteria (each 0–5; higher is better):

| Criterion | A. Crates stay in the pack; Companion consumes by git rev | B. Crates move to the Companion; prometheus-cli repoints to a Companion git dep | C. Closure extracted to a third shared repo both consume |
|---|---|---|---|
| Goal text fidelity (Goals 2 and 5 as written) | 2 | 5 | 3 |
| HMA control-plane contract holds without revision | 5 | 1 | 3 |
| Dependency direction (pack is a consumer of the Companion node, not the reverse at build level) | 5 | 1 | 4 |
| Release coupling (a pack release does not require a Companion release and vice versa) | 3 | 1 | 4 |
| Migration risk to signed state and the 15 installed prometheus-family plists (assessment gap 4 table) | 4 | 2 | 2 |
| **Total (25)** | **19** | **10** | **16** |

A leads C by 12% of the scale and B by 36%. By the pipeline's rule the A-versus-C gap is under 15% and therefore **contested**; this is not a stack choice, so `pmpo-elicit` was not invoked, and the choice was routed to the operator.

**Operator decision (2026-09-02, final after two clarifications): a fourth option, D.** None of A, B, or C was right, because all three assumed the question was "who owns the crates". The operator's question is "what is product and what is operational core":

- The pack is **open source and complete on its own**: skills, hooks, the `prometheus` CLI, kbd-runtime as the local signed KBD authority, and every functional service stay, and every kbd-* skill works fully with no Companion. The pack certifies fully without it (the 2026-08-29 reconciliation spec already requires daemon-free certification).
- The Companion is the **paid control and extension framework**: sync, CRDT replication, P2P, discovery, orchestration, monitoring, and the run-guarantee supervisor move there. Third parties extend the pack the same way the Companion does, from their own repositories, through a contract the pack publishes.
- **The pack never depends on the Companion**, at build or install time; the Companion consumes the pack's open crates by git rev. That is option A's dependency mechanism applied to the crates that stay, and it keeps HMA's `prometheus-control-plane.json` valid as written because kbd-runtime stays.
- Optional capability is **discovered at runtime, never assumed**. With the Companion present, kbd-* gains sync and remote signed commands through the discovered endpoint; absent, nothing changes and nothing warns.

The scoring table above is retained as the record of a framing error: it scored ownership, not the product boundary. What moves: sovereign-sync in full (daemon, REST/MCP/SSE control plane, multi-project router, remote signed commands, P2P, gossip, replication, `--mode mcp`), sovereign-client, storage-provider's `iroh_docs.rs` adapter, kbd-mobile (mobile sync wire; skill-ffi drops or feature-gates that dependency without importing a paid crate), the sharing LaunchAgent and systemd unit, the `--sharing` install path, and the three `sync-*` skills, which become the Companion's own skill plugin and the first worked example of third-party extension. What stays: everything else, including kbd-runtime (Loro is its local journal format, which is function), the CLI, skill-index, learner-model, the storage-provider trait and local adapters, and every service where it runs today. New scope this phase carries: the pack must publish an **open, versioned integration contract** (control-endpoint discovery in the CLI transport chain, hook bundle extension points, a service manifest the supervisor can adopt, the connected-skill-package declaration), because without it a paid product would need private knowledge of the pack and third parties could not follow. Decisions D-01 and D-03 through D-14 hold, because they concern running the node in a different binary, not ownership; cand-016 is adopted in the Companion-to-pack direction only. One fact, not advice: sovereign-sync's MIT history is already public and stays so. That is the disposition, not the footprint. The footprint the G5 removal change must touch is the assessment's name-based list (33 non-doc files plus 42 doc files), of which `grep -rl sovereign-sync scripts shared/scripts shared/launchagents shared/systemd` gives 20 in the install and service layer alone: `scripts/{install-binaries.sh,install-skills-flat.sh,install-mcp-services.sh,install-sovereign-sync-sharing.sh,install-system.js,docs-sync.mjs,check-mcp-health.sh,certify-prometheus-exec-use-cases.py}`, `shared/scripts/{detect-toolchain.sh,service-probe.sh}`, four `shared/scripts/tests/*`, the sovereign-sync plist and systemd unit, and the four other plists (liter-llm-api, forge-mcp, surface-bridge, pk-cherry) that reference sovereign-sync in ordering or environment. The plan must re-derive this list with the same command at write time and decide per installer branch whether it switches to the Companion or is deleted.

Regardless of option, `substrate/kbd-runtime` (14,877 LOC, zero substrate deps, ed25519 envelopes, exclusive journal lock) remains the authority implementation; nothing researched replaces it.

### 2.3 Node hosting and external surface (gap 6) — verdict: adapt sovereign-sync into a library spawned from the Tauri setup hook; reference clawdesk

Tier 1 code search surfaced `clawdesk/clawdesk` (MIT, 3 stars, last push 2026-03-23): a 25-crate workspace whose `crates/clawdesk-tauri/src/lib.rs` (lines 527-620) spawns an embedded HTTP/WS gateway crate inside `tauri::Builder::setup`, registers tray commands `get_gateway_health` / `refresh_gateway_health`, and degrades when the gateway store fails to open. It is the precedent the assessment said did not exist. Tauri docs (Tier 2) confirm the mechanism: `tauri::async_runtime::spawn` from `setup`, state via `app.manage`. know-me's `gen_ui_server_axum` (382 LOC) remains the reference for the AG-UI run/events SSE split.

Surface: the node keeps its Unix-socket REST/MCP/SSE surface (with `--tcp` optional) because the `prometheus` CLI transport chain, the three `sync-*` skills, and the Codex/Kimi harnesses already consume it; Tauri IPC is added only for the Companion UI. This requires that Companion spec §15 (AG-UI via Tauri events) **be amended at spec stage** to "Tauri events for the UI, SSE for external callers"; the spec on disk is unchanged and Companion AGENTS.md §0.7 forbids silent scope change. Rework classes when re-hosting: remove `unwrap()` (Companion AGENTS.md L518, repo-wide), exact pins, iroh in the Infrastructure layer, credential model per §17 and §2.7 below, and a port or socket allocation the spec lacks.

**MCP is the exception to "the surface survives."** sovereign-sync's MCP server is **stdio-only** (`main.rs:11` "MCP server over stdio — for Claude Code, Kimi, Codex, OpenCode, BossFang"; `main.rs:244` `serve_stdio`), it is served by the daemon binary that option A stops shipping as a service, and it is registered by `install-skills-flat.sh:541-552` into the user-level `mcp-servers.json` as `sovereign-sync --mode mcp`. The Companion spec §4.1 (L269) is explicit that stdio MCPs "remain stdio because they are spawned by the AI client", not by the Companion, so an in-process node cannot be that server. Two dispositions are possible: (a) keep a thin `sovereign-sync --mode mcp` **stdio shim** in the pack whose tools proxy to the node's Unix socket, which preserves the harness registrations and the `sync-*` skills but keeps a small binary in the pack and must be reconciled with Goal 2's "replacing the sovereign-sync daemon"; or (b) drop MCP mode and update `install-skills-flat.sh`, `install-mcp-services.sh`, and the three `sync-*` skills to use the socket via the CLI. Recommended: (a) for v1, because `mcp_client_pool.rs` and the `UAR_SKILL_SERVICE_URL` passthrough already exist for exactly this proxying shape, and the harness registrations are outside this phase's control on user machines. Either way it is a build item and part of the G5 footprint; the spec's §4.1 MCP list must name it.

### 2.4 Workspace layout (Q1) — verdict: adopt one root workspace; reject the hand-mirrored `[patch]` pattern

Two consumers were examined. know-me keeps a separate `desktop/src-tauri` workspace with a hand-mirrored `[patch]` table and documents "desktop build breaks while cargo check is green" as the consequence. graph-explorer keeps one workspace with `desktop` as a member. HMA's `scaffold-tauri-tray.sh:95-98` prescribes `members = ["crates/<name>", "src-tauri"]`. Companion spec Appendix A assumes a skill-pack superworkspace that does not exist and pins iroh 0.30; it must be rewritten to whichever ownership option §2.2 resolves to. A developer-only `[patch."https://github.com/..."]` block pointing at local checkouts is acceptable for iteration but must not be the committed default.

### 2.5 State-location continuity (gap 8) — verdict: adopt `dirs_next` + `PROMETHEUS_DATA_DIR` in the node; add a credential-store continuity check

Tauri's path resolver (`app_data_dir()`, `app_config_dir()`, `app_local_data_dir()`) joins the platform directory with the **bundle identifier**, so a Companion using it would write under `~/Library/Application Support/<bundle-id>/`, not `.../prometheus/`. kbd-runtime resolves the data root as `PROMETHEUS_DATA_DIR` → `dirs_next::data_local_dir()` → `temp_dir()/prometheus-data` (lib.rs:2979-2982); the hosted node must keep calling `dirs_next` directly.

The device key is **not** primarily a file. `managed_device_key_path()` (lib.rs:303-308) is `XDG_CONFIG_HOME` or `~/.config/sovereign-sync/device-key.json` and is only the managed/legacy fallback; the canonical store is the OS credential store, entry `prometheus-kbd-device` (lib.rs:3419, 3448; lib.rs:2973 "Canonical runtimes use the host credential store, unless an explicit headless key file is configured"; `PROMETHEUS_DEVICE_KEY_FILE` is the mode-0600 headless alternative, lib.rs:3429). Revision 1 wrongly cited `dirs_next::config_dir()`, which on macOS is `~/Library/Application Support`, a different directory.

This creates a continuity risk the filesystem check does not cover. keyring 3.6.3's macOS backend (`keyring-3.6.3/src/macos.rs:33,58,70`) uses `security_framework`'s `find_generic_password` / `set_generic_password`, which is the legacy login keychain with a **per-item application ACL**: when a binary other than the creator reads the item, macOS prompts the user to allow or always-allow. The daemon at `~/.local/bin/sovereign-sync` created `prometheus-kbd-device`; a Companion-hosted node is a different signed binary. For the GUI-hosted node the consequence is one interactive prompt, which the plan must anticipate in first-run UX. The failing direction is the **headless** node (§2.9), which cannot answer a prompt; its remedy already exists, `PROMETHEUS_DEVICE_KEY_FILE` (lib.rs:3429), a mode-0600 key file. Keychain access groups are not a remedy here: they apply to the data-protection keychain and require entitled, bundled binaries, which an unbundled launchd daemon is not. The plan must include a two-process check (daemon-written state and key read by a Companion-hosted node) covering the data root, the journal, and the credential item, with the remedies being ACL trust for the GUI node, the key file for headless hosts, or a one-time re-enrollment.

### 2.6 Service model and supervision (gap 12, G4) — in-process versus external evaluated per service; adopt the HMA aggregator; build the supervisor actor

The Companion spec is unambiguous that its target is in-process: §4 "running the substrate in-process as a Rust library", §4.1 a four-process runtime, §16.2 `ChildKind: InProcess | ExternalSidecar`, §16.4 listing surreal-memory, prometheus-knowledge, prometheus-research, forge-rs, liter-llm, sovereign-sync, surface-bridge, skill-index, and prometheus-exec each "(in-process)" with surreal as the one optional sidecar, and §25.2 "One substrate binary | Keep the 15+ processes". Revision 1 recommended supervising ten external processes without evaluating that against the spec. The per-service evaluation, using what each service is today in the pack:

| Service | Today | In-process feasible now? | Recommended v1 kind | Why |
|---|---|---|---|---|
| sovereign-sync | pack crate, bin+lib, axum | yes | InProcess | already a library; this phase's subject |
| skill-index | pack crate (142 LOC) | yes | InProcess | pure library, path dep of sovereign-sync |
| surface-bridge | pack crate, axum on 7890 | yes, with a router merge | InProcess (after merge) | axum 0.8 library; merging routers removes a port |
| prometheus-exec | pack crate `crates/prometheus-exec` + `exec-service` UDS | likely; `exec-service` is a library | ExternalSidecar first, InProcess later | sandbox (Seatbelt) semantics and UDS contract in `execution-sidecar-service` spec must be preserved |
| prometheus-research | pack crate, axum on 7891, launchd | yes, with router merge | ExternalSidecar first | separate plist installed by install-binaries.sh; low priority |
| liter-llm-api | `tools/liter-llm` submodule binary on 4000 | only by linking the proxy crate | ExternalSidecar | separate repo with its own config discovery (`--config` contract); v1 should not link it |
| forge-mcp | `tools/forge-rs` submodule binary on 8943 | only by linking | ExternalSidecar | separate repo |
| pk-cherry (prometheus-knowledge) | `tools/prometheus-knowledge` submodule binary on 8942 | only by linking | ExternalSidecar | separate repo, owns the pk wiki |
| surreal-memory-native | `tools/surreal-memory-server` submodule on 23001 | only by linking | ExternalSidecar | separate repo |
| surrealdb-native | third-party binary on 28000 | no | ExternalSidecar | spec already makes it the sidecar |
| learning-worker, codex-skills-sync, hooks-logrotate, prometheus-nudge, pk-lint, mem0-compress | timers | as tokio tasks | InProcess timers or stay launchd | spec is silent; needs disposition |

Conclusion, revised under operator decision D-02: **every pack service stays where it runs today**, launchd- or systemd-managed and installed by the pack, because the pack must be complete without the Companion. The Companion's supervisor therefore **adopts** them rather than hosting them: it reads a service manifest the pack publishes (the existing LaunchAgent and systemd templates are already most of that manifest), probes health, restarts through `launchctl kickstart` or `systemctl --user`, and owns configuration and the tray state, which is exactly Companion spec §18.5.9's Supervisors panel. The only thing the Companion runs in-process is its own node (sovereign-sync as a library, discovery, the health aggregator). The "In-process feasible?" column above stays as evaluation evidence, but the spec's "(in-process)" labels in §16.4 and the "one substrate binary" row in §25.2 must be amended to "adopted external services plus one in-process node"; the §16 `ChildKind` enum already has `ExternalSidecar` for this. Distribution of service binaries stays with the pack's installers; the Companion installs only its own node.

No crate was found that supervises a heterogeneous set of local children with dependency ordering, backoff, and typed health; process-spawn crates cover only the spawn. HMA ships `assets/templates/tauri-tray/health-aggregator/` (tokio-only, five states) and `launchagent-supervisor` (ThrottleInterval ≥ 15, KeepAlive dictionary, PID-file lock, rendered plist). The §16 supervisor actor is build work; every retry branch must trace to a named failure (Companion AGENTS.md §0.2). `tauri-plugin-autostart` 2.5.1 is rejected as the outer restart authority: it writes a login-item plist without `KeepAlive`/`ThrottleInterval`, so it cannot restart the app on crash, which is the failure HMA's skill exists to prevent. launchd, via a rendered plist, stays the outer restart authority for the Companion (spec §4.1/§25.1).

### 2.7 Device key and operator credentials (§17) — verdict: adopt the incumbent keyring 3.6.3 for the device key; adopt tauri-plugin-stronghold for operator credentials per spec

The consumer's manifest answers the device-key question: `substrate/kbd-runtime/Cargo.toml:29-35` pins **`keyring = "=3.6.3"`** with `apple-native`, `sync-secret-service`+`crypto-rust`, and `windows-native` features per platform, and the Companion spec §14.1 likewise stores the Ed25519 keypair "in the OS secure store". Revision 1 framed this as Stronghold-versus-keyring with keyring as a reference alternative; that missed the incumbent. Consequences: keyring 3.6.3 enters the Companion's dependency graph the moment kbd-runtime is consumed, so it belongs in the Companion `versions.toml` pins (a human edit); proposing keyring 4.2.0 (Tier 3: 22.9M downloads, updated 2026-08-29) alongside it would be a second major version of the same crate and is rejected for this phase. The keychain-ACL continuity issue in §2.5 follows directly.

`tauri-plugin-stronghold` 2.3.2 (updated 2026-08-31) is what Companion spec §17 mandates for **operator credentials and provider keys**, and is adopted for that scope only. Its password-derived vault does not affect the node's device key, which kbd-runtime already handles, and headless hosts already have the `PROMETHEUS_DEVICE_KEY_FILE` path.

### 2.8 Pairing (gap 13) — verdict: adopt iroh EndpointId authentication + tickets; reference SPAKE2 for the short-code UX; reject Noise

sovereign-sync has no Noise (`grep -il noise` over src and Cargo.toml: nothing); iroh authenticates peers by Ed25519 EndpointId over QUIC/TLS 1.3, and `export_ticket/import_ticket/authorize_endpoint` implement admission. The Companion spec's "Noise + Iroh" wording (L66, L122, L222) is a documentation error to correct at spec stage. The spec's 6-digit code + QR + operator approval UX can sit on top: `spake2` 0.4.0 (RustCrypto PAKEs, Tier 3: 1.2M downloads, updated 2026-01-25; 0.5.0-pre.0 published) turns a short code into an authenticated key exchange, which is how `clawdesk-discovery` does it. Reference, not adopt: spec decides whether QR-encoded tickets suffice for v1.

### 2.9 Test harness (G6) — the existing baseline is not the gate; build a two-process harness with a headless-hosted node

What `sovereign-sync/tests/domain_sync.rs` proves must be stated exactly. Its node fixture (lines 113-121) binds "a real iroh endpoint bind, but never `.start()`ed — no actual gossip join or network I/O beyond the local socket bind", and the replication tests hand each envelope "to node B's incoming-message handler" by function call (lines 183-185) inside one test process. Three of its four async tests are two-`AppState` tests, not two-process or two-network-node tests, and `surreal_memory_is_rejected_before_any_bytes_are_prepared` is single-node. It is a valuable **library-level regression** for envelope encoding, signature verification, and CRDT merge, and must keep passing, but it is not evidence that "two-node runs prove discovery, CRDT convergence, a signed KBD command delivered over P2P" (Goal 6), and the repository's integration-only policy requires real process and network boundaries. Revision 2 of this analysis overstated it; the assessment's gap 11 had already called it a "baseline to preserve", which was right for the narrower claim.

The G6 harness is therefore **build work**: launch two real node processes through their production entry points, locally (never hosted CI): one Companion binary built with the spec's `headless` preset (Companion spec §4.2, Appendix A.2 L4019, no window and no Stronghold unlock) and one second instance or the pack daemon, on separate data roots, then assert address lookup (mDNS on loopback or a bootstrap entry), a real gossip join, a signed KBD command submitted through the `prometheus` CLI transport chain on one node and observed on the other, and the supervisor's health surface. The "desktop preset" node from revision 2 is withdrawn from the harness: a GUI process is not what a local gate should launch. `domain_sync.rs` stays as the fast library regression beneath it.
