## Findings and decisions

### G1 — Prevent bytecode in immutable hook generations

The compiled runner (`crates/prometheus-hook/src/main.rs:105`) and shell fallback (`shared/scripts/hook-runtime-v1.sh:182`) both execute the generated Bash dispatcher. Cold bootstrap uses Node and shell before entering this path. Emit `export PYTHONDONTWRITEBYTECODE=1` in `scripts/generate-harness-adapters.js:renderDispatcher`, then regenerate owned outputs. This inherited setting covers Python descendants, including detached feeders, and overrides a caller's value of 0. Also cover directly invoked learning wrappers (`sessionstart-learning.sh`, `subagentstart-learning.sh`, `subagentstop-learning.sh`) and direct `learning_write.py` use; set bytecode suppression before local imports and pass it into Python subprocess environments where needed. `-B` is useful defense but its command-line flag alone does not propagate into a new interpreter.

Preserve strict generation integrity; do not ignore __pycache__ in manifests or modify installed caches. Existing contaminated generations remain contaminated. An approved refresh can publish a new generation identity from the changed dispatcher bytes; installer inspection shows staging/new-generation verification precedes activation, without requiring payload verification of the previous active generation in that transaction. Do not delete the old payload manually. Final acceptance must install a scratch packaged generation and exercise compiled, shell and direct production paths, with temporary caller workarounds unset and a hostile inherited bytecode setting.

Primary Python documentation: https://docs.python.org/3.11/using/cmdline.html#envvar-PYTHONDONTWRITEBYTECODE . Context7 /python/cpython/v3.11.14 confirmed interpreter behavior; local Python versions may differ but this setting is longstanding.

### G2 — Why Codex regrows memory_summary.md

Installed CLI reports 0.158.0. The official `rust-v0.158.0` annotated tag peels to `064c6b8c737f5b41d171fdda80bd9ef10ad06eb3`; research used that release, not main. Its `codex-rs/memories/write/src/start.rs:33-37` guards startup on ephemeral mode, the memory feature and root-session eligibility. It does not guard on generate_memories or use_memories. Startup runs phase 1 and then phase 2; an empty extraction batch does not stop global consolidation.

`codex-rs/config/src/types.rs:295-330` defines generate_memories as the eligibility default for newly created threads, while use_memories controls prompt use. Historical eligible threads and stored stage-1 outputs remain. Phase 2 claims a global consolidation job, reads stored outputs and starts the writer; its own internal agent configuration disables generation and use while still writing artifacts. Therefore neither setting alone is the startup kill switch.

Read-only local inspection found features.memories=true, generate_memories=false and no explicit use_memories. For corroboration, database and WAL files were copied to private scratch directories and only timing/count metadata queried there; scratch databases were removed. No live SQLite handle or lesson body was read. The v1 store retained 23 stage-1 outputs and a completed global consolidation from 2026-10-05 05:39:47 to 05:48:44 UTC. The archived summary's mtime is 05:48:25.852782 UTC, within that window. This strongly supports consolidation as the regrowth mechanism. It is not a PID-level attribution or controlled reproduction: copies taken during concurrent writes are best-effort snapshots, and the desktop engine version was not established from the CLI version. Evidence: evidence/codex-memory-metadata.json.

Proposed settings: features.memories=false, memories.generate_memories=false, memories.use_memories=false. The feature switch blocks new startup pipelines; the other settings constrain eligibility/read-side use. Running sessions retain cloned configuration and may finish queued work, so an approved machine change must be paired with session restart/drain and effective override inspection.
