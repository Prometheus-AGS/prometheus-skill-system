# Plan — team-aware-learning-memory-impl

**Backend:** native-kbd (`.kbd-orchestrator/project.json`). **Driver:** `kbd-apply` begin-task/end-task per task.
**Inputs:** `assessment.md` (2 review rounds), `analysis.md` (D-1…D-7 + binding amendments), `library-candidates.json`, spec handoff (25 changes, 82 tasks).

## Ordering rationale

- Rounds are dependency layers computed from each change's `Depends on` (no cycles; checked).
- **Cargo serialisation:** within a round, Rust changes (pk, surreal-memory, A5a/E1 cargo checks) run one at a time; gates refuse to start while another cargo/rustc runs (exit 2).
- **Critical path to the alpha gate:** A1 → A3 → A5a → B3 → B4 → B5 (6 changes, 22 tasks; A2 and A4 must also merge before A5a). By task count B1 → B2 → B3 → B4 → B5 ties at 22 tasks, so it is also critical. The phase end is set by D1b, which waits on operator-owned A5b, not by B5.
- **E1's mini request** supersedes any still-open A5b request (one pin request on versions.toml at a time); if A5b has landed it is a fresh request.
- **PR flow:** each change is one PR from its own worktree; the user merges; a dependent change starts after its dependencies are merged on `origin/main` (rebasing and regenerating generated outputs).
- **Operator-owned:** A5b (mini pins + versions.toml). D1b is blocked on it; G1's mini half is BLOCKED-ON-OPERATOR until it lands.
- **User-confirmed outward steps:** tag pushes (A5a, E1), mini issues (A5b, E1), the live MEMORY.md partition (B6), sandbox GitHub issue creation (C4).
