# Intersession communication · engineering analysis

**Recommendation.** Keep the Full pack’s signed project journal as the record of work. A second session on the same machine reads it directly. A session on another device can receive the work through an explicitly addressed Companion push. To confirm delivery, read the signed event from the receiving device. For two sessions using the same authoritative local team-state file, the named recipient can accept the existing task handoff. Cross-device journal sync carries work history. It does not transfer ownership in that separate team-state file.

### When the journal advances but the checkout stays stale

Companion imports the signed history before refreshing the checkout’s waypoint. A refresh error is logged and the import still returns success. The refresh is attempted only when new events were inserted, so an identical retry cannot be relied on to repair that waypoint. For Spec, require a recipient-side comparison of journal and projection revisions and a supported way to regenerate a stale projection from the durable history. Verify recovery after a temporary filesystem write failure and confirm the command appears exactly once. This uses the runtime’s existing projection comparison and writer. [Import path](/Volumes/T7/Projects/prometheus/prometheus-companion/crates/sovereign-sync/src/kbd_control.rs)

## How to prove the result

1. **Full only.** Install with no Companion endpoint. Session A commits and exits; B reads the signed event and next task. For ownership acceptance, both sessions address the very same authoritative team-state file. Read it independently after accept, unchanged replay and stale rejection. Check the next authorized KBD update separately. Replay and stale-owner cases must leave the expected owner and revision. Restart a watcher between commits, then check for gaps and duplicate effects. Preserve standalone installation, KBD doctor and signed audit checks.
2. **Version pair.** Use the installed writer to enroll a second operator, share the trusted baseline between independent test stores, then open both stores through the rebuilt Companion. Check the event and the enrolled keys. The previously supported journal and the new co-operator history must both open. A binary that encounters an unsupported event must preserve the history and identify the incompatible reader.
3. **Peer delivery.** Run Companion’s existing real-process verifier. B must initially be stale. Send the signed update explicitly to B, correlate audit and SSE with A's event, compare frontiers, restart B, then retry. Independently exercise a rejected target, a paired but unauthorized signer, a revoked device, and a wrong project. Each rejection must leave the receiver’s journal unchanged. Send the same command while disconnected, then reconnect and verify eventual delivery once.
4. **Network and scale.** A passing three-process test establishes interoperability on one host. Use two physical hosts on the expected LAN to claim cross-machine discovery, with distinct identities and journals. Include a realistically sized offline backlog before claiming coverage of this Full project. Use only disposable credentials and project data in the test.

The original peer test, schema rejection, pack continuity, disposable service recovery and standalone read/write results remain the baseline. No dependency was upgraded and no post-upgrade test was run during analysis. The nine standalone doctor failures and 130 existing Full OpenSpec failures remain separately visible. A successful peer run cannot clear those suites. [Assessment and receipts](assessment.md)

## Alternatives and constraints

A separate message broker would introduce another service and another record to reconcile when offline. A Git handoff or shared transcript alone cannot prove a recipient applied a signed event. A transport-level acknowledgment alone cannot show that B parsed the writer’s schema. The existing project mechanisms cover those responsibilities with fewer dependencies. Direct conversational messaging beyond work updates and accepted task handoffs remains a separate product question.

The verifier currently provisions an offline copy of a trusted baseline. Specify a supported bootstrap procedure before calling a new-device installation self-service. The behavior of physical LAN discovery and the encoded size of a representative backlog are open measurements. The local workspace manifest, lockfile and peer verifier were untracked in the Companion checkout during this inspection; preserving the narrowly reviewed files will be necessary for reproducible release builds.

Research used the established Rust stack and the checked-in or working-tree sources, upstream repositories, Context7 API documentation and the registry records for the locked versions. The registry marks iroh 1.1.0 and Loro 1.13.9 as available and not yanked. Full release source, local diagnostics and the lockfile are the basis for the compatibility decision. Upstream docs support API capabilities only.
