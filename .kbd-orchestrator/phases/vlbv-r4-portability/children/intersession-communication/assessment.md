# Basic KBD communication between sessions

Assessed November 24, 2026 against the registered Full pack checkout, the local Companion working tree, and Full pack CLI 1.15.0. The first useful outcome is that a person can finish a step in one session and open another to see what happened and what to do next. When the second session runs on a paired machine, the person must also be able to tell whether that machine actually received the update.

## What sessions share

| Situation | Expected behavior | Evidence or gap |
|---|---|---|
| Two fresh CLI processes on one machine use the same registered project and local authority | A committed update survives process exit. The second session reads its phase, revision and event ID through status and audit. A running session can follow events with watch. | Verified fresh status and audit on this real child with remote control disabled and its configured socket absent. Both saw the assessment at revision 2577. Earlier isolated installation independently verified two Ed25519 event signatures. Live watch, restart catch-up and concurrent writers still need coverage. |
| A role in one harness hands work to a role in another | The existing handoff names the task, revision, destination, next action and evidence. The source retains ownership until the destination accepts. A stale or repeated acceptance cannot assign the same task twice. | The Full pack already defines handoff-create and handoff-accept. Exercise two independent sessions through these entry points. Handoff files, Git changes and attachments have their own distribution path. KBD journal convergence alone does not prove those files reached another checkout. |
| Two enrolled devices use Companion | The sender selects one paired endpoint and one registered project. An explicit signed push carries the committed update. The receiver can show the same command ID, event ID, signature, integrity hash and converged frontier. Its waypoint also advances. | The first run proved the CLI reached A. Neither node started peer networking. The repaired code builds. On rerun the old embedded KBD reader failed on a valid operator_granted event before discovery could be checked. Peer replication remains unverified. |
| Companion is absent, unavailable or restarts | Local commitments remain readable and writable. Local success can be reported immediately. Confirming cross-device delivery requires evidence on the other device. When Companion returns, the operator can explicitly send the missing history. | Current CLI defaults to local control. With an explicitly selected missing socket, status and audit silently returned the local journal at revision 2577. In the same configuration watch exited 1 on connection failure. For a remote write with an uncertain reply, reconcile its original command ID before replay. An authorization or semantic rejection must be surfaced. Test the loss of a connection both before dispatch and after commit. |
| A peer or signer lacks authority | An unpaired peer, a device revoked for this project, or a recipient with a different project must not apply the event. No success claim or ownership transfer may be inferred from a transport receipt. | Existing verifier exercises a third unpaired node. Add paired-but-project-unauthorized, revoked-signer and wrong-project cases separately so an early pairing rejection cannot hide an enrollment bug. |

The communication surface is signed work state and explicit handoffs. A chat transcript, general-purpose mailbox, automatic background publication or a new hosted service is unnecessary for these outcomes. An offline machine can retain its own work until a transport is available. Distinct devices without a transport cannot promise immediate delivery. If independently addressed free-text messages are wanted, that is a separate product decision.

## Implementation sequence

1. **Bring Companion’s reader up to the supported writer.** The workspace pins Full pack revision `cfbc262b47ce794cb2ea845c64dc33e70b10e890`. The published Full `v1.17.0` tag resolves to `acd029107533c07a661a7e3ad90eb28834688afa` and contains `EventKind::OperatorGranted`. Align the pack dependencies and Cargo.lock at the intended supported release, review the affected API and dependency changes, then build the real binaries. Keep both enrolled operators and the original signed history in the scenario. Establish a reader/writer compatibility fixture per supported release and return an actionable error when a reader meets an unsupported event. Never discard unknown signed events to make startup succeed.
2. **Keep a single local authority.** Use the existing project UUID, registered checkout, signed journal, idempotent command ID and work-claim machinery. Use status and audit for startup catch-up. Existing watch polls the event reader and deduplicates event IDs within its process; a consumer that needs continuity across restarts should resume from durable state and deduplicate by event ID. When a requested remote read falls back, identify the data source while preserving the existing status and audit JSON contracts. Give watch a documented disconnect and catch-up behavior. Never use a successful fallback to establish remote application. Preserve existing authority rejections and distinguish them from service unavailability.
3. **Finish the peer path already in the working tree.** Pair the devices, enroll their independent project keys and provision a common trusted baseline. Use the real pack CLI to commit an identifiable change, sign the addressed push, and confirm it through B’s own audit and event stream. Replaying the same request must preserve its receipt and event count. Use the preexisting peer verifier, then extend coverage only where an acceptance case below is missing. Document the supported baseline bootstrap procedure; the current verifier copies a trusted seed while stopped.
4. **Expose useful outcomes to operators.** Show the project, revision, command ID and whether the change was recorded locally, sent, or observed on the recipient. The receiving session can recover the active task and next action. If it must take ownership, perform the revision-checked handoff. A sending-side HTTP 200 or 201 by itself does not establish remote application.

## Proposed local acceptance packet

| Check | Required evidence |
|---|---|
| Local-only, two sessions | Two fresh processes, separate working sessions and the same registered authority. A writes and exits with the socket absent. B reads the exact signed event and next action, and can make the next authorized update. Exercise watch restart and simultaneous writes or claims, preserving both legitimate events or explicitly reporting a conflict. |
| Handoff | A creates a real packet, B accepts it at the expected task revision. Verify owner and revision in a third read. Repeat unchanged acceptance and compare receipt, owner and revision. Separately submit a stale acceptance, verify rejection, and read back the unchanged owner. Check that evidence references resolve. |
| Supported-release compatibility | Latest supported pack writer enrolls B as co-operator. Both independent Companion processes open the resulting history, replay the enrollment and report ready. A prior supported signed journal still opens. |
| Paired replication and restart | Use the production binaries and installed CLI. B starts at the seed frontier and cannot see the new command before the push. Afterward B’s audit, event stream and projection match A. Stop and restart B and verify the event remains. The three-process verifier exercises distinct authorities on one host. Before claiming physical LAN support, repeat pairing, discovery and the matched-event check across two machines on the supported network. |
| Offline and ambiguous delivery | Commit while Companion is absent, start Companion, explicitly sync, and match the destination event. Interrupt a response after submission and reconcile the original command ID. Exact push retry adds no event. |
| Denials and isolation | Independently reject an unpaired endpoint, an unauthorized or revoked project signer, and an incorrect project. Inspect the destination’s unchanged frontier and audit. |
| Regression | Retain local Full-pack installation, standalone KBD projection checks, the pack-to-Companion continuity test and Companion’s disposable-service recovery test. Evaluate the doctor with the profile actually installed. Publish counts and remaining failures from the unfiltered doctor and strict OpenSpec checks separately. |

Run the agreed packet after implementation, against local disposable identities and production binaries. Passing requires every adopted check to run and meet its assertions. A skipped peer test, a local fallback, or a health-only response cannot satisfy a peer scenario. The parent’s existing phase contract covers different work. This child needs its own adopted acceptance contract before execution or certification. The later implementation should also restore full-profile doctor success where the real dependencies are installed, and either repair or explicitly track each pre-existing strict-validation failure. Until those checks pass the projects cannot be described as all green.
