**Research Date:** 2026-07-03  
**Researcher:** Prometheus Deep Research Agent  
**Topic:** Google's Open Knowledge Format (OKF), A2UI Protocol, and the Emerging Landscape of AI-Native Document Standards  
**Purpose:** Foundational research for enhancing the Prometheus Skill Pack's `deep-research` skill specification

## Executive Summary

Google has announced a new open document standard specifically designed for LLM wikis and AI agent knowledge consumption: the **Open Knowledge Format (OKF)**, published as v0.1 on **June 12, 2026**, by Google Cloud's Data Cloud team (Sam McVeety and Amir Hormati). OKF is a vendor-neutral, human- and agent-friendly specification that formalizes the "LLM-wiki" pattern (originally articulated by Andrej Karpathy) into a portable, interoperable format.

OKF is **not** the same as Google's A2UI protocol (a UI rendering protocol). They are complementary standards serving different layers of the agent stack. OKF packages knowledge; A2UI packages user interfaces.

The current landscape of AI-native document formats is converging around markdown-based standards with structured frontmatter, with OKF emerging as the most formalized standard from a major tech company. The Prometheus `.research` package format should align closely with OKF conventions while preserving its own research-specific extensions.

## 1. What Is Google's New Document Standard for LLM Wikis?

### Primary Finding: The Open Knowledge Format (OKF)

On **June 12, 2026**, Google Cloud published the **Open Knowledge Format (OKF) v0.1**, an open specification that represents curated knowledge as a directory of **Markdown files with YAML frontmatter**. [^1][^2]

> *"OKF is an open, human- and agent-friendly format for representing knowledge — the metadata, context, and curated insight that surrounds data and systems. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both."*
> — OKF v0.1 Specification, Google Cloud [^3]

### Core Design Principles

OKF is built on three deliberately minimal principles: [^1]

1. **Minimally Opinionated** — Only one required field: `type`. Everything else is left to the producer. The spec defines the interoperability surface, not the content model.
2. **Producer/Consumer Independence** — A bundle hand-authored by a human can be consumed by an AI agent. A bundle generated by one LLM can be queried by another. The format is the contract.
3. **Format, Not Platform** — OKF is not tied to any cloud, database, model provider, or agent framework. It requires no proprietary account or SDK.

### What Problem Does OKF Solve?

In most organizations, AI-relevant knowledge is catastrophically fragmented: [^1]

- Metadata catalogs with their own APIs
- Wikis behind login walls
- Code comments, docstrings, notebook cells
- Shared drives
- Inside the heads of senior engineers

When an AI agent needs to answer "How do I compute weekly active users from our event stream?", it must assemble the answer from scattered, mutually incompatible surfaces every time. OKF solves this by providing a **lingua franca** — a shared format that anyone can produce and anyone can consume. [^1][^4]

### What Google Ships With OKF

Google published reference implementations alongside the spec: [^1][^2]

| Component | Description |
|-----------|-------------|
| **Enrichment Agent** | Walks a BigQuery dataset, drafts an OKF concept document for every table/view, then enriches each with citations, schemas, and join paths via a second LLM pass |
| **Static HTML Visualizer** | Turns any OKF bundle into an interactive graph view in a single self-contained file — no backend, no install |
| **Sample Bundles** | Three ready-to-browse bundles: GA4 e-commerce, Stack Overflow, and Bitcoin public datasets |
| **Knowledge Catalog Ingestion** | Google Cloud's Knowledge Catalog updated to ingest OKF bundles directly |

### Clarification: What OKF Is NOT

| Misconception | Reality |
|---------------|---------|
| A Google product requiring GCP | No — it's Apache 2.0 licensed and vendor-neutral [^3] |
| A replacement for RAG | No — it's complementary. OKF stores curated knowledge; RAG retrieves raw chunks [^5] |
| A ranking signal for SEO | No — OKF is not a search optimization tactic [^6] |
| A fixed taxonomy | No — type values are not centrally registered [^3] |
| The same as A2UI | No — A2UI is a UI protocol; OKF is a knowledge format [^7] |

## 2. The Open Knowledge Format (OKF) v0.1 in Detail

### Bundle Structure

An OKF bundle is a directory tree of markdown files: [^3]

```
path/to/bundle/
├── index.md              # Optional. Directory listing for progressive disclosure.
├── log.md                # Optional. Chronological history of updates.
├── <concept>.md           # A concept at the bundle root.
└── <subdirectory>/
    ├── index.md
    ├── <concept>.md
    └── <subdirectory>/
        └── …
```

### Reserved Filenames

| Filename | Purpose | Status |
|----------|---------|--------|
| `index.md` | Directory listing for progressive disclosure | MUST NOT be used for concepts |
| `log.md` | Update history | MUST NOT be used for concepts |

### Concept Document Frontmatter

The only **required** field is `type`. All others are optional: [^3]

```yaml
---
type: <Type name>                  # REQUIRED
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI for the underlying asset>
tags: [<tag>, <tag>, …]           # Optional
timestamp: <ISO 8601 datetime>    # Optional last-modified time
# … other producer-defined key/value pairs
---
```

**Recommended fields (in priority order):**

| Field | Purpose |
|-------|---------|
| `title` | Human-readable display name |
| `description` | Single sentence summary; used by index generators and previews |
| `resource` | URI that uniquely identifies the underlying asset |
| `tags` | YAML list of short strings for cross-cutting categorization |
| `timestamp` | ISO 8601 datetime of last meaningful change |

### Conventional Body Sections

| Heading | Purpose |
|---------|---------|
| `# Schema` | Structured description of an asset's columns/fields |
| `# Examples` | Concrete usage examples, often as fenced code blocks |
| `# Citations` | External sources backing claims in the body |

### Cross-Linking

Concepts link to each other using standard markdown links. Two forms are supported: [^3]

- **Absolute (bundle-relative) links**: `See the [customers table](/tables/customers.md)`
- **Relative links**: `See the [neighboring concept](./other.md)`

A link from concept A to concept B asserts a *relationship*. The specific kind of relationship is conveyed by the surrounding prose, not by the link itself. Consumers MUST tolerate broken links.

### Index Files (`index.md`)

Index files enumerate directory contents to support progressive disclosure: [^3]

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

### Log Files (`log.md`)

Log files record chronological history of changes: [^3]

```markdown
# Directory Update Log

## 2026-05-22
* **Update**: Added new BigQuery table reference for [Customer Metrics](/tables/customer-metrics.md).
* **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).

## 2026-05-15
* **Initialization**: Created foundational directory structure.
```

### Conformance Criteria

A bundle is conformant with OKF v0.1 if: [^3]

1. Every non-reserved `.md` file contains a parseable YAML frontmatter block
2. Every frontmatter block contains a non-empty `type` field
3. Every reserved filename follows the described structure when present

Consumers MUST NOT reject a bundle because of missing optional fields, unknown types, unknown additional keys, broken cross-links, or missing `index.md` files.

### Versioning

OKF uses `<major>.<minor>` versioning: [^3]

- **Minor bump**: Backward-compatible additions (new optional fields, new conventional headings)
- **Major bump**: May make breaking changes (renaming required fields, changing reserved filenames)

Bundles may declare their target version via `okf_version: "0.1"` in the bundle-root `index.md` frontmatter.

## 3. Google A2UI Protocol: Relationship to Document Standards

### What Is A2UI?

**A2UI (Agent-to-User Interface)** is an open-source declarative protocol from Google, released in December 2025 (v0.8, now v0.9 as of April 2026), that enables AI agents to generate rich, interactive user interfaces. [^7][^8]

> *"A2UI is an open standard and implementation that allows agents to speak UI. An agent does not output HTML or JavaScript. It outputs an A2UI response, which is a JSON payload that describes a set of components, their properties and a data model."*
> — Google A2UI Documentation [^7]

### A2UI Is NOT a Document/Knowledge Format

A2UI is fundamentally different from OKF. It serves a different layer in the agent stack:

| Layer | Standard | Purpose | Format |
|-------|----------|---------|--------|
| Discovery | `llms.txt` | Point AI systems to important pages | Markdown |
| Instructions | `AGENTS.md` / `CLAUDE.md` | Tell coding agents how to behave | Markdown |
| **Knowledge** | **OKF** | **Package curated knowledge for agents** | **Markdown + YAML** |
| Tool Access | MCP | Connect agents to tools and data | JSON-RPC |
| Agent Communication | A2A | Cross-organizational agent messaging | JSON |
| **UI Rendering** | **A2UI** | **Generate dynamic user interfaces** | **JSON** |
| Transport | AG-UI | Real-time agent-frontend sync | SSE / HTTP |

### A2UI Technical Design

A2UI uses a **declarative JSON format** (JSON Lines/JSONL for streaming) with these properties: [^7][^8]

- **Security-first**: Data format, not executable code. No UI injection risk.
- **LLM-friendly**: Flat list of components with ID references, enabling incremental generation
- **Framework-agnostic**: Same payload renders on React, Angular, Flutter, SwiftUI, Lit
- **Progressive rendering**: Supports streaming UI updates

The four primary message types are: [^9]

1. `createSurface` — Create a new surface and specify its catalog
2. `updateComponents` — Add or update UI components in a surface
3. `updateDataModel` — Update application state
4. `deleteSurface` — Remove a UI surface

### How A2UI and OKF Complement Each Other

In a full agent application stack, the two standards work together:

1. An agent uses **OKF bundles** as its knowledge base (what it knows)
2. When the agent needs to present information to a user, it generates an **A2UI payload** describing the UI components (how to show it)
3. The client renders the A2UI payload using its native component library
4. The agent continues to reference OKF knowledge when responding to user interactions

## 4. Current State of AI-Native Document Formats

### The Landscape of AI-Readable Formats (2026)

The ecosystem has evolved rapidly from "human-readable docs that AI happens to parse" to "deliberately AI-native document standards." Here are the key formats as of mid-2026: [^10][^11][^12]

| Format | Creator | Purpose | Status | Format |
|--------|---------|---------|--------|--------|
| **OKF** | Google Cloud (June 2026) | Knowledge bundles for AI agents | v0.1, active | Markdown + YAML |
| **llms.txt** | Jeremy Howard / FastAI (Sept 2024) | Discovery metadata for AI crawlers | ~950 domains adopted | Markdown |
| **llms-full.txt** | llms.txt community | Full content companion to llms.txt | Widely used | Markdown |
| **AGENTS.md** | AI coding community | Project instructions for coding agents | De facto standard | Markdown |
| **CLAUDE.md** | Claude Code community | Project context for Claude Code | De facto standard | Markdown |
| **skill.md** | Mintlify / community | Product capability descriptions | Growing adoption | Markdown |
| **pricing.md** | Resend, Auth0, WorkOS (2025) | Machine-readable pricing | Emerging convention | Markdown |
| **auth.md** | WorkOS | Agent authentication flows | Emerging convention | Markdown |
| **agent-permissions.json** | Marro et al. | Robots.txt-style agent permissions | Academic proposal | JSON |
| **MCP (Model Context Protocol)** | Anthropic (Nov 2024) | Tool/data access for agents | v1.0, rapidly adopted | JSON-RPC |
| **A2A (Agent-to-Agent)** | Google (April 2025) | Cross-organizational agent communication | Active | JSON |
| **A2UI** | Google (Dec 2025) | Declarative UI generation | v0.9, active | JSON |
| **CTX** | Context Protocol community | Context passing between agents | Emerging | JSON |

### Key Distinctions Between OKF and Other Formats

| Format | What It Does | How It Differs from OKF |
|--------|-------------|--------------------------|
| `llms.txt` | Single file pointing to important pages | OKF is a whole directory of linked concepts; llms.txt is a map |
| `AGENTS.md` | Convention file for one repo's coding agent | OKF generalizes to any domain, multi-file, with typed concepts |
| `skill.md` | Describes what a product can do | OKF is the knowledge itself, not capability descriptions |
| `MCP` | Protocol for tool access | OKF is about knowledge content, not tool invocation |
| `A2A` | Agent-to-agent communication | OKF packages knowledge; A2A transports messages |

## 5. Karpathy LLM Wiki Pattern and Convergence with OKF

### The Original LLM Wiki Pattern

Andrej Karpathy (co-founder of OpenAI, former Tesla AI director) articulated the LLM Wiki pattern in a widely-shared gist. The core insight: [^13][^14]

> *"LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass. The bookkeeping that causes humans to abandon personal wikis is exactly what LLMs are good at."*
> — Andrej Karpathy, LLM Wiki Gist [^13]

The pattern involves:
1. Keeping notes as structured markdown files
2. Pointing a coding agent (like Claude Code) at the folder
3. The LLM reads files, finds relevant content, and gives grounded answers
4. The agent incrementally builds and maintains the wiki — updating cross-references, filing changes, maintaining indexes

### How OKF Formalizes the Pattern

OKF explicitly acknowledges its lineage: [^3]

> *"OKF is intentionally close to several established patterns: LLM 'wiki' repositories that use markdown + frontmatter as agent-readable knowledge bases; personal knowledge tools like Obsidian and Notion; and 'metadata as code' approaches. OKF differs primarily in being specified — pinning down the small set of rules needed for interoperability without dictating tooling."*
> — OKF v0.1 Specification [^3]

### Convergence Indicators

| Community Practice | OKF Equivalent | Status |
|--------------------|---------------|--------|
| `index.md` as content catalog | OKF `index.md` | Formalized in OKF |
| `log.md` as chronological record | OKF `log.md` | Formalized in OKF |
| Markdown + YAML frontmatter notes | OKF concept documents | Formalized in OKF |
| Cross-linked wiki pages | OKF cross-linking with markdown links | Formalized in OKF |
| Obsidian vaults for agent memory | OKF bundles as interoperable format | Migration path emerging |
| `AGENTS.md` / `CLAUDE.md` | OKF generalizes the pattern | Complementary |

### Community Adoption Signals

- **Obsidian**: The Obsidian community has been doing markdown-with-YAML-frontmatter knowledge management for years. OKF explicitly acknowledges this lineage. [^4]
- **Tolaria**: A Mac/Linux desktop app that turns markdown folders into AI-native knowledge bases with Git versioning — could adopt OKF as its interchange format. [^4]
- **AgentToolkit/altk-evolve**: An open-source project already aligning its `.evolve` knowledge store with OKF. [^15]
- **WitsCode**: Maintains an open-source OKF conformance suite and validator. [^16]
- **WordPress**: A free plugin generates OKF bundles from published posts and serves them at `/okf/`. [^6]

## 6. Google Deep Research, Gemini Deep Research, and NotebookLM Output Formats

### Gemini Deep Research Output Formats

Google's Gemini Deep Research (released December 2024, expanded 2025) generates: [^17]

- **Structured reports** with introduction, main sections, analysis, conclusions, and properly formatted citations
- **Export options**: Google Docs for editing and sharing
- **Audio Overviews**: Podcast-style discussions of findings (NotebookLM-style)
- **PDF/Image Upload**: Can combine public web data with proprietary documents

The output is **not** a specific new document standard like OKF. It is a research report that can be exported to conventional formats (Google Docs, Markdown). [^17]

### NotebookLM Output Formats

NotebookLM (Google's research notebook product) supports these formats: [^18][^19][^20]

**Source Uploads:**
- `.txt`, `.md`, `.csv`, `.html`, `.htm`, `.json`
- PDFs (native through NotebookLM interface)
- YouTube videos (transcripts, public videos with captions)
- Google Docs, Slides, PDFs from Google Drive

**Export Formats (via third-party tools and official features):**
- Reports: Exportable as Google Docs, with tables exportable to Sheets
- Mind Maps / Infographics: PNG files
- Audio Overviews: M4A files
- Video Overviews: MP4 files
- Slide Decks: PDF or PowerPoint files
- Notes: Markdown, Word, PDF (via export tools)
- Flashcards/Quizzes: Not directly downloadable; requires third-party tools
- Full notebook backup: JSON or ZIP [^18]

**NotebookLM Deep Research (added late 2025):**
- Generates reports as markdown (.md) files
- Currently **cannot** be directly downloaded within NotebookLM interface (a noted limitation) [^20]
- Sources found by Deep Research can be added to the notebook with checkboxes

### Key Insight

Neither Gemini Deep Research nor NotebookLM Deep Research produces OKF-formatted output natively. However, the **content** they generate (markdown reports with structured sections and citations) is highly compatible with OKF ingestion. A research report could be manually or automatically converted into an OKF bundle by:

1. Creating a concept document for each major finding
2. Using YAML frontmatter to tag concepts with `type: ResearchFinding`
3. Adding citations under `# Citations` sections
4. Cross-linking related concepts
5. Maintaining a `log.md` of research sessions

## 7. Emerging Standards for "AI-Readable Documents" and "Agent Documents"

### The Stack of AI-Native Standards

The ecosystem is organizing into a layered stack: [^10][^11]

```
┌─────────────────────────────────────┐
│  Layer 5: UI / Presentation         │  A2UI, Open-JSON-UI
├─────────────────────────────────────┤
│  Layer 4: Knowledge Content         │  OKF, Obsidian vaults, wiki repos
├─────────────────────────────────────┤
│  Layer 3: Discovery & Capability    │  llms.txt, skill.md, pricing.md, auth.md
├─────────────────────────────────────┤
│  Layer 2: Tool & Data Access        │  MCP, A2A
├─────────────────────────────────────┤
│  Layer 1: Transport & Communication │  AG-UI, HTTP/SSE, WebSocket
└─────────────────────────────────────┘
```

### Key Emerging Conventions

1. **Content Negotiation for Markdown**:  
   Servers can detect `Accept: text/markdown` headers and return markdown instead of HTML. This is becoming the industry standard for tools like Claude Code and OpenCode. [^21]

2. **Single-File Corpus (`llms-full.txt`)**:  
   In addition to per-page files, many sites now generate a single `llms-full.txt` that concatenates everything for agents that prefer one large fetch over crawling. [^22]

3. **Markdown URL Support**:  
   Support viewing pages as Markdown by adding `.md` to the URL (e.g., `example.com/docs/page.md`). Used by nuqs, FastHTML, Mintlify, GitBook. [^21]

4. **AI Prompts in Documentation**:  
   Docs now include AI prompts users can paste directly into their agent. Examples: Clerk Docs, Sentry Docs, Supabase Docs. [^21]

5. **MCP Servers for Documentation**:  
   Projects run their own MCP servers (e.g., Astro Docs MCP Server) so AI tools can connect directly to documentation for up-to-date information. [^23]

### Google Cloud Knowledge Catalog Integration

Google Cloud's Knowledge Catalog (formerly Dataplex) is an AI-powered data catalog that provides a dynamic knowledge graph. [^24] It has been updated to **ingest OKF bundles directly** and serve them to agents. This creates a production-grade consumption path for OKF: [^2]

1. Produce OKF bundles from your data sources (BigQuery, custom pipelines)
2. Ingest them into Google Cloud Knowledge Catalog
3. Agents query the catalog for contextual knowledge

## 8. Recommendations: Aligning Prometheus `.research` Package with OKF

### The Prometheus Context

The Prometheus ecosystem already has several relevant components:

- **Karpathy LLM Wiki**: Uses `index.md` and `log.md` — the exact conventions OKF formalizes
- **Feynman Learning Loop**: Produces concept mastery data that could be packaged as OKF concepts
- **Deep Research Pipeline**: Generates `.research` knowledge packages that should be compatible with emerging standards
- **Learner Model**: Tracks concept mastery; could export learner profiles as OKF bundles

### Specific Recommendations

#### 8.1 Adopt OKF as the Base Format for `.research` Packages

The Prometheus `.research` package should be structured as an **OKF bundle** with research-specific extensions: [^3]

```
research-package/
├── index.md                     # OKF standard: catalog of all research artifacts
├── log.md                       # OKF standard: chronological research session log
├── findings/
│   ├── index.md
│   ├── finding-001.md           # Each finding = one OKF concept
│   ├── finding-002.md
│   └── …
├── sources/
│   ├── index.md
│   ├── source-001.md            # Each source = one OKF concept
│   └── …
├── knowledge-graph/
│   └── …                        # Graph data (JSON, optional)
├── artifacts/
│   └── …                        # Non-markdown artifacts (PDFs, images, data files)
└── manifest.json                # Research-specific metadata (not part of OKF core)
```

#### 8.2 Use OKF Frontmatter with Research-Specific Extensions

```yaml
---
type: ResearchFinding          # OKF required field
title: "Google OKF Standard for LLM Wikis"
description: "Google's Open Knowledge Format formalizes the Karpathy LLM wiki pattern."
tags: [google, okf, llm-wiki, document-standard, knowledge-format]
timestamp: 2026-07-03T16:00:00Z
# Prometheus extensions:
research_id: "prom-2026-0703-001"
confidence: 0.95
verification_status: "verified"
source_count: 24
research_stage: "Report"       # Planner, Search, Retrieve, Collect, Verify, Resolve, Graph, Cite, Report, Export
---
```

#### 8.3 Map Deep Research Pipeline Stages to OKF

| Deep Research Stage | OKF Concept Type | OKF Location |
|---------------------|------------------|--------------|
| Planner | `ResearchPlan` | `plan/plan-001.md` |
| Search | `SearchQuery` | `queries/query-001.md` |
| Retrieve | `SourceDocument` | `sources/source-001.md` |
| Collect | `Evidence` | `evidence/evidence-001.md` |
| Verify | `Verification` | `verify/verify-001.md` |
| Resolve | `Resolution` | `resolve/resolve-001.md` |
| Graph | `KnowledgeGraph` | `graph/graph-001.md` |
| Cite | `Citation` | Part of `Citations` section in findings |
| Report | `ResearchFinding` | `findings/finding-001.md` |
| Export | `ResearchPackage` | `index.md` + bundle |

#### 8.4 Use `index.md` for Progressive Disclosure

Following OKF conventions, the root `index.md` should enable progressive disclosure: [^3]

```markdown
# Prometheus Research Package: Google OKF Investigation

## Research Questions

* [What is Google's new document standard for LLM wikis?](findings/okf-definition.md) — Google's Open Knowledge Format (OKF) v0.1
* [How does A2UI relate to document standards?](findings/a2ui-relationship.md) — A2UI is a UI protocol, not a knowledge format
* [What is the AI-native document format landscape?](findings/ai-native-formats.md) — OKF, llms.txt, AGENTS.md, MCP, and more

## Findings

* [Finding 001](findings/finding-001.md) — OKF is the formalization of Karpathy's LLM wiki pattern
* [Finding 002](findings/finding-002.md) — OKF requires only `type` field; everything else is optional
* …

## Sources

* [Source 001](sources/source-001.md) — Google Cloud OKF announcement
* [Source 002](sources/source-002.md) — OKF v0.1 Specification
* …

## Update Log

* [Session Log](log.md) — Chronological research activity
```

#### 8.5 Use `log.md` for Research Session History

```markdown
# Research Update Log

## 2026-07-03
* **Search**: Executed 12 parallel searches on OKF, A2UI, and AI-native formats
* **Synthesis**: Drafted findings for all 8 research questions
* **Report**: Generated structured markdown report with 24 citations

## 2026-07-02
* **Planning**: Decomposed topic into 8 research questions
* **Search**: Initial search for "Google new document standard LLM wikis"
```

#### 8.6 Ensure Conformance Without Breaking Flexibility

OKF v0.1 is intentionally permissive. The Prometheus `.research` package should: [^3]

- **MUST**: Include `type` in every concept document's frontmatter
- **MUST**: Reserve `index.md` and `log.md` for their specified purposes
- **SHOULD**: Include `title`, `description`, `tags`, and `timestamp`
- **MAY**: Include arbitrary additional frontmatter keys (research-specific metadata)
- **MUST**: Tolerate broken cross-links (research may reference not-yet-written concepts)
- **SHOULD**: Use standard markdown links for cross-referencing
- **SHOULD**: Include `# Citations` sections for external source attribution

#### 8.7 Integrate with Existing Ecosystem Tools

| Tool/Platform | Integration Strategy |
|---------------|----------------------|
| **Google Cloud Knowledge Catalog** | Export `.research` packages as OKF bundles for ingestion |
| **Obsidian** | `.research` packages can be opened directly as Obsidian vaults |
| **NotebookLM** | Import OKF concept documents as sources; export research back to OKF |
| **Claude Code** | `CLAUDE.md` + OKF bundle = complete agent context |
| **MCP Servers** | Build an MCP server that exposes OKF bundle navigation as tools |
| **Git Version Control** | OKF bundles are natively diffable and mergeable |

#### 8.8 Differentiate from OKF Where Research-Specific Semantics Matter

OKF is deliberately minimal. The Prometheus `.research` package may need richer semantics that OKF doesn't prescribe: [^3]

| OKF Non-Goal | Prometheus Research Need | Resolution |
|-------------|--------------------------|------------|
| No fixed taxonomy | Research findings need typing | Use `type` field with research-specific values (`ResearchFinding`, `SourceDocument`, `Verification`) |
| No trust model | Research needs confidence scores | Add `confidence` extension field in frontmatter |
| No temporal validity model | Findings may become stale | Add `valid_until` or `verification_date` extension fields |
| No contradiction handling | Research may find conflicting sources | Add `contradictions` section in body or `conflicts_with` cross-link |
| No query infrastructure | Research needs searchability | Add `manifest.json` with indexed metadata; OKF bundle itself is file-searchable |

These extensions should be documented as **Prometheus Research Profile** — a domain-specific OKF profile that extends the base format without breaking conformance.
