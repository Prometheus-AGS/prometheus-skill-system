# Generated output ownership

`scripts/generate-harness-adapters.js` declares its emitted files.
`scripts/generate-skill-system-distribution.js` derives its package directories
and marketplace files from `skill-system.json`. Each generator retains
`--list-outputs`: one repository-relative path per line, with a trailing `/` for
directory ownership. `scripts/generated-paths.mjs` combines and sorts these
declarations for consumers. There is no separately maintained root list.

A declaration states policy. Asking its own generator to print it again does
not independently verify that the policy covers the materialized output.

The distribution generator now observes filesystem mutation destinations while
materializing into its disposable tree, then walks the **entire** tree using
`lstat`, including symlinks and empty directories. It checks that:

- Every content or metadata mutation belongs to a declared output. Directory
  creation may also provide the ancestors needed to reach an owned output.
- Every materialized entry belongs to declared ownership, apart from those
  necessary ancestor directories. Walking only declared roots would miss stray
  files; this walk starts at the temporary tree root.
- Every required declared output exists with its declared kind. Required
  package directories must contain materialized content.
- Every observed output and operation is classified as generated by the same
  `generatedPathOwner` function that rebase conflict classification uses.

The mutation observer refuses destinations outside ownership before mutation,
including direct synchronous `fs` writes outside the generator's copy/write
helpers. It also refuses writes escaping the temporary tree or following a
copied symlink. The observer restores the original filesystem bindings on both
success and failure. It is scoped to this generator's synchronous materialization
process; it is not an agent tool restriction or a general filesystem sandbox.

The resulting ownership audit runs for both generation and `--check`, before
anything is published. `--check` additionally compares the materialized package
contents, modes and bytes with the checkout's owned outputs; a removed required
file in the checkout remains a drift failure. `--list-outputs` prints declarations
without materializing or auditing and is not acceptance evidence.

`rebase-regenerate.sh` asks `generated-paths.mjs --classify-conflicts` to classify
unmerged paths before changing them. That consumer reads NUL-delimited Git paths
and uses mode `160000` in all index stages and HEAD to identify source gitlinks.
It rejects generated ownership overlapping a gitlink and leaves source or
gitlink conflicts for the caller to resolve. Initialization state, directory
presence and submodule worktree contents do not determine ownership. It never
initializes, updates, stages or otherwise mutates unrelated submodules.

After generated-only conflicts have been resolved, the helper regenerates,
performs the existing local validators and stages only the declared output
paths. Exit codes remain `0` for resolved and locally validated paths, `1` for
source conflicts or validation failures, and `2` for an unusable environment or
no active rebase/merge. The helper leaves continuing the rebase or committing the
merge to the caller.

Acceptance belongs to the completed-production boundary in
`change-ldd-12-integration-rollout`. Its disposable Git worktrees must exercise
real generation and rebase regeneration with initialized and uninitialized
gitlinks, a required-output deletion, and an undeclared generated write. Source
implementation alone does not establish those acceptance results.
