Open your coding agent this morning. Ask it to fix a flaky test. It does — cleanly, with a clear explanation of the root cause. Close the laptop. Open it tomorrow. Same agent, same repo, a different but related failure. It has no idea what happened yesterday.

It doesn't know yesterday's failure was a missing Redis-client mock. It doesn't know you spent twenty minutes teaching it how clap 4 handles global flags. It doesn't know the prompt you spent an hour crafting last month — the one that finally got it writing idiomatic Tokio — was load-bearing for exactly that task and nothing else. Every session starts from near-zero. CLAUDE.md, AGENTS.md if you wrote one, your git history, and whatever vector store you've bolted on: that's the entire universe of "memory" available to a 2026-era coding agent.

RAG helps a little. Embeddings retrieve text that looks similar to your query. But embeddings are a black box. You can't read them, diff them, or tell me with a citation what the agent knew when it made a decision last Tuesday. For a system you're willing to put in front of a regulated client, that opacity isn't a rough edge — it's disqualifying.

There's a better pattern. Andrej Karpathy sketched the shape of it; the open-source agent ecosystem has spent the last year quietly filling it in. What follows is how the prometheus-skill-pack turns that sketch into a running system — and the engineering it takes to close the loop without losing the plot.

01 · The Pattern

A wiki a human can read, compiled by the model that uses it

The idea is simple enough to be misleading. The prometheus-knowledge crate implements it like this:

~/.prometheus/knowledge/
├── raw/          ← inbox (watched by FSEvents / inotify)
│   └── *.md      ← drop files here
└── wiki/         ← compiled articles
    ├── universal-agent-runtime.md
    ├── mempalace-rs.md
    └── ...

Every wiki article is a single markdown file with YAML frontmatter — an id, tags, links to related entries, the session it came from, a revision number. There's no vector database. Search is TF-IDF. Every fact in the system traces to a file you can cat, diff, and git blame.

The inversion that matters is who maintains the knowledge base. In a normal RAG setup, you curate the corpus. In this pattern, the AI builds and maintains it for you. A librarian watches the inbox, calls an LLM to compile raw notes into structured entries, writes the result to the wiki. The LLM is the compiler. The human owns the substrate. The substrate is plain text.

That's the entire insight. Everything past this point is engineering.

02 · The Engine

Three storage tiers, four learning layers, one policy gate

The loop runs execute → evaluate → compile → optimize → distribute. Four layers, each doing a distinct job, each feeding the one above it.

EXECUTE → EVALUATE → COMPILE → OPTIMIZE → DISTRIBUTE, gated at L3→L4 by policy, not vibes

L1 — Memory: the hot tier

SurrealDB with HNSW vector indexes, dual transport over MCP and HTTP, 40-plus tools: knowledge graph traversal, mem0-compatible scoped memory, TaskStreams with model-aware token budgeting, mindmaps. What lives here is working memory — session state, recent relationships between concepts. What doesn't live here is durable, human-readable engineering knowledge. That's L2's job.

L2 — Knowledge: the Karpathy tier

The cold tier. Flat files, TF-IDF, git-trackable. This is the layer that compounds, because it's cheap to write — an LLM call plus flat-file IO — cheap to read — TF-IDF scales without an embedding server — and expensive to lose, because it lives in your dotfiles, in git, on every machine you own.

L3 — Optimization: the layer most teams skip

Every skill is treated as a DSPy signature. Captured traces become a dataset. BootstrapFewShot or MIPRO runs against it and produces a candidate — never an applied change. This is the load-bearing claim of the whole architecture:

The system can learn, but it cannot rewrite its own skills in production without passing policy.

If you're building an agentic system and you don't have an explicit policy layer between "the agent discovered a better way" and "the agent updated its own prompt," stop and build that layer first. Everything else is decoration.

L4 — Distribution: the install path

Skills install across ten platforms — Claude Code, OpenCode, Codex, Kimi Code, MiniMax, Zed, Cursor, Windsurf, Roo, Cline, Gemini CLI. Skills.toml declares what a project wants; Skills.lock records what resolved. The portability is the point. The abstraction that makes the learning portable is the skill, not the model.

03 · Proof, Not a Demo Reel

See it close in five minutes

Theory is cheap. Here's how you watch the loop close yourself, in any tool that's already on your machine — Claude Code, Codex, OpenCode, Kimi Code, or a plain chat surface. Two phases. Teach it something specific, then prove a session that's never seen this conversation already knows it.

Phase 1 — teach it something only you know

Pick a fact you'd otherwise re-explain every session. For this walkthrough, the fact is concrete: a launchd-managed agent returning 401 recovers with launchctl kickstart -k gui/$(id -u)/<label>. Save it:

cat > /tmp/respawn-trick.md <<'EOF'
When a launchd-managed agent starts returning 401, 405, 500, or gets
stuck in `state=spawn scheduled`, the correct recovery command is:

    launchctl kickstart -k gui/$(id -u)/<label>

The -k flag kills the existing process first; kickstart then asks
launchd to spawn a fresh one. Discovered 2026-06-30 — the openai-proxy
on :8181 returned 401 "token_expired" after 5 days of uptime. The
kickstart command cleared it in 3 seconds.
EOF

kbd-close /tmp/respawn-trick.md

Wait for the receipt: ✓ compiled → Launchd respawn trick for transient agent failures. That's your proof the knowledge is in the wiki.

Phase 2 — prove a fresh session already knows it

Restart the tool. Open a session with no history of Phase 1. Ask:

"My openai-proxy just started returning 401. What do I do?"

If the agent reaches for the wiki and hands back the exact launchctl kickstart command without you pasting a thing — that's the loop. Not a stronger model. Not coincidence. The system remembered, and the new session had no other way to know it.

If it doesn't work

Check three things in order: did the entry land (pk list | grep respawn), did the session-start hook fire (cat ~/.prometheus/last-open-snapshot.txt), and is the compile proxy actually up (curl localhost:8181/v1/models). If all three check out, you just ran a clean demo.

04 · The Honesty Gate

The Feynman loop, and why self-graded fluency doesn't count

A wiki you can't verify is a wiki you can't trust. The system's answer to "did the agent actually learn this?" maps Feynman's explain-grade-gap-relearn cycle onto the same Spec → Plan → Execute → Reflect shape that governs everything else here. Mastery closure requires three things, not one:

  1. The grade passes — overall score ≥ 0.7 and misconceptions are fully absent
  2. Transfer holds — two novel problems solved at 0.7 or better, each
  3. Retention is scheduled — a spaced-repetition check at 24 hours or more

Self-reported fluency never closes a loop. You cannot write a learner model that says "I think I understand this" and have the system accept it. The gate is external, source-grounded, corpus-anchored — and it's structured to lead with errors, not compliments. A real grade looks like this:

{
  "scores": { "completeness": 0.85, "accuracy": 0.50, "clarity": 0.90, "misconceptions_absent": 0.0 },
  "overall_score": 0.56,
  "gaps": [{
    "dimension": "accuracy",
    "description": "Claimed tokio::spawn requires 'static. It requires Send +
      'static on the future, not the closure. The bound is misattributed.",
    "corpus_ref": "src:tokio-docs::spawn"
  }],
  "passed": false
}

An anti-sycophancy check runs before any grade is written. Hedging language — "minor issue," "just a small point" — gets rewritten to direct language: "factual error," "missing coverage of X." The grade is for the learner's benefit, not the author's comfort. That's not a feature bolted on top. It's a structural property the rest of the system depends on.

05 · Write-Back

How the loop survives the gap between sessions

The single most important sequence in the system runs at the end of every session. The order isn't a style preference — it's a correctness constraint. Each step consumes the output of the one before it.

the four-step stop hook, in the order it has to run

What this buys you: the loop doesn't require anyone to remember to run it. It fires at the natural boundaries — session start, session end, a periodic nudge — and every boundary writes to the same store. The agent that wakes up tomorrow morning is not the same agent that went to sleep. It's a strictly stronger agent, with a strict superset of memory and an updated skill catalog.

What compounding looks like, traced across three sessions

N

The failure happens once

Auth tests fail. The agent fixes them. The session summary records the actual cause: a missing Redis-client mock in tests/auth/setup.rs — any test hitting Redis got connection refused instead of the fixture value.

→

The stop hook fires

The pattern matches the testing skill's known failure modes. A candidate file lands in ~/.prometheus/skill-updates/. Nothing is applied yet — it's a proposal, not a change.

N+1

A different service, same monorepo

Context priming retrieves the Redis-mock learning before you ask. The agent doesn't reproduce the failure. The testing skill's coverage expands because the failure never happened a second time.

✓

You review and approve

pmpo-skill-creator --update testing proposes an in-place patch: Redis mock setup becomes a first-class step in the test-fixture lifecycle. You approve it. The skill is now strictly stronger than it was an hour ago.

N+2

Someone who never saw any of this

A different operator, a different repository, a fresh install of the skill pack. The testing skill already includes the Redis-mock step. The failure doesn't happen there either — and they never read a line of the original session.

That's cross-session compounding at the structural level. Not emergent, not magic — engineered, and at the one step that rewrites the system's own instructions, explicitly gated by a human.

06 · Skills That Propose Updates to Themselves

The meta-loop, and the line it doesn't cross

If compounding stopped at "the wiki gets bigger," you'd have a documentation system, not a learning system. What makes it a learning system is pmpo-skill-creator's update mode — a skill that reads its own learning log and proposes a patch to another skill's manifest.

From the skill's own manifest

update — in-place skill refinement from learning patterns. Improves an existing installed skill using accumulated patterns from the continuous-learning pipeline. Requires explicit user approval before any file is modified.

The system's ability to change itself is conditional on a human saying yes. That's the Cedar Skill-Mutation policy, enforced at the workflow layer instead of the runtime layer. Five evolution perspectives feed into it — competitive parity, domain trend-watching, the next logical product step, a three-gate idea-validation pipeline, and a self-learning perspective that consumes the same JSONL the write-back sequence produces. That fifth one is what this article is about. The loop closes on itself.

07 · The Critic

Why the grader can't be the same model that did the work

Self-evaluation only works if the critic is separate from the producer. Grade your own work and you will pass — humans and LLMs both do this, even when the work is wrong. The fix is structural: a different model, a different process, a different context.

producer / critic separation — the load-bearing decision in the whole grading pipeline

The model choice is the decision that carries the most weight. Use the strongest available model as the grader — not the same model as the producer, not something smaller and cheaper. The producer's blind spots are usually exactly what the learner needs feedback on; a grader with the same blind spots just reinforces them. A grade costs one round-trip. A failed mastery gate costs the next Feynman recursion. The economics favor paying for the better grader.

Verified live against a real explanation that looked correct, the grader caught four things a self-grade would have missed entirely: an invented mechanism ("the respawn trick clears cached auth state" — it doesn't), a misattributed signal ("kickstart sends SIGTERM" — the corpus never claims that), a boundary error (recommending the respawn trick for server-side auth failures it can't fix), and a hard-coded assumption that didn't match the corpus's actual path convention. None of those are obvious. None would survive a self-grade. All four were caught in a single round-trip.

If you take one idea from this whole piece, take this one: the loop does not work if the producer and the critic are the same model.

08 · The Honest Accounting

What this doesn't solve yet

The system reports readiness by evidence class rather than a synthetic percentage. Artifact, disposable-runtime, installed-service, and external-deployment claims have different proof and must not be collapsed into one number. The remaining operational gaps are worth naming plainly:

GapWhat it means in practice
Single-maintainer bus factorThe architecture is sound; the cognitive load of holding it in one head is visible. Plan for the day that's not sustainable.
No external production deploymentsRuns in development and staging today. It hasn't been audited inside a regulated production environment.
Optimization layer is human-gated by designCorrect tradeoff, but it means most teams won't actually exercise the dspy-rs layer day to day. The primary learning signal in practice is the wiki write-back, not optimization.
Cedar policy is necessary and tediousThe defaults are sane. Tuning the bundle for your environment is real work you should budget for, not skip.

None of that is a reason to skip the pattern. It's a reason to budget honestly for the work of adopting it.

09 · The Morning After

A private pulse, not a feed

OpenAI shipped ChatGPT Pulse in late 2025 — an async overnight pass over your chat history that surfaces five to ten cards each morning. Gated to the highest tier, hosted by OpenAI, silent on whether your data trains future models. The loop described above gives you durable memory. It doesn't give you a morning briefing. So I built one — a single bash script, five subcommands, zero dependencies beyond bash, python3, and curl.

The system prompt that curates the cards is explicit about what not to do:

Ground every card in something concrete from the user's actual activity. Don't invent URLs. Skip generic "AI is changing the world" filler — the user is already in the work. Five to ten cards total; if the activity is thin, three honest cards beat eight padded ones.

The most valuable card type isn't a release announcement — it's a flag the system raises on its own, grounded in something written weeks ago that would otherwise have been forgotten. A gap between local test confidence and CI enforcement. A symlink that turned out to be a real symlink and not a copied directory. Small, specific, true. That's the bar.

It is not a notification stream, and it isn't trying to be. ChatGPT Pulse ends each day with "that's all for today." This one ends each run by writing a file that the next session-open will surface. The cost is one cheap LLM call and, optionally, a few web searches. It is not a replacement for the wiki — the wiki is durable, the pulse is ephemeral by design. A feed wants you back tomorrow. A pulse wants to be useful once and let you get back to work.

10 · Closing

The shape of the system, if you're building one

None of the individual pieces here are novel. The value is in the integration, and in refusing to skip the parts that are tedious. If you're building a production agentic system and you want it to actually improve across sessions, this is the shape to converge on:

  1. A flat-file knowledge base as the epistemic substrate. Plain markdown, git-trackable. No vector DB for the durable tier.
  2. A semantic graph store for working memory during a session — SurrealDB, Postgres with pgvector, whatever you already run.
  3. A write-back hook chain that fires in a strict order at every session boundary. The order is the correctness guarantee.
  4. An external grader for any self-evaluation. The model that produced the artifact cannot be the model that grades it.
  5. A policy layer between "the agent found an improvement" and "the agent changed its own instructions." Cedar, OPA, whatever you trust. Default deny.
  6. Skill portability across harnesses. The same description works in Claude Code, OpenCode, Codex, Kimi Code. The harness isn't the abstraction — the skill is.
  7. A heartbeat between sessions. The system writes to memory even when no one's at the keyboard. The loop runs in the gaps, not just at the boundaries.

Build that, and tomorrow's session is strictly stronger than today's — not by a percentage point, by a structural property. Yesterday's wiki is already in context. Yesterday's learning log is already in memory. Yesterday's approved skill updates are already in the catalog.

The system you're running next year will be a different system than the one you started with — and it'll be that way because you engineered the loop, not because the model spontaneously got better.

That's the whole posture. Not a feature. A way of building.
