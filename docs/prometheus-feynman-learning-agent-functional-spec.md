## 1. Purpose and Scope

This document defines the functional requirements, user flows, system behaviors, and data contracts for the Prometheus Feynman Learning Agent (PFLA). It serves as the contract between product, design, engineering, and QA teams.

**Scope**: Covers all learner-facing features, agent behaviors, admin capabilities, and platform integration points. Excludes non-functional requirements (performance targets, infrastructure sizing) which are defined in the Architecture Document. The marketplace features (Coach Catalog, Creator Studio, Master Certification, Live Coaching, and Video Conferencing) are defined in the **Functional Specification Addendum** (`prometheus-feynman-learning-agent-functional-spec-addendum.md`).

**Related Documents**: `prometheus-feynman-learning-agent-architecture.md` (Architecture), `prometheus-feynman-learning-agent-functional-spec-addendum.md` (Marketplace: Coach Catalog, Creator Studio, Master Certification, Live Coaching, Video Conferencing).

## 2. Actor Definitions

| Actor | Description | Primary Goals |
|---|---|---|
| **Learner** | A user who wants to master a subject using the Feynman Technique. | Create goals, explain concepts, identify gaps, achieve mastery. |
| **AI Tutor Agent** | The autonomous learning agent that orchestrates the Feynman loop. | Generate explanations, grade responses, identify gaps, recurse. |
| **AI Improvement Agent** | The Karpathy Loop agent that optimizes pedagogy. | Run experiments, measure LVS, propose curriculum changes. |
| **Platform Admin** | Operations staff managing the SaaS platform. | Monitor health, manage subscriptions, review experiment outcomes. |
| **MCP Server** | External tool server providing search, compute, code execution. | Serve tool requests via MCP protocol. |

## 3. Feature Catalog

### 3.1 Goal Management (FEAT-001)

**Description**: Learners create, manage, and track learning goals.

**User Stories**:
- US-001.1: As a learner, I can create a new learning goal by entering a subject (e.g., "Quantum Mechanics") so that I have a container for my learning journey.
- US-001.2: As a learner, I can set a target proficiency level (novice / peer / expert) so that the agent knows my ambition.
- US-001.3: As a learner, I can see a curriculum tree generated by the agent for my goal so that I know what concepts to learn in order.
- US-001.4: As a learner, I can mark a goal as complete or archive it so that my dashboard stays organized.
- US-001.5: As a learner, I can set a recursion floor (concepts I already know) so that the agent doesn't waste time on fundamentals.

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-001.1 | Goal creation accepts a subject string and optional target proficiency. | Must | Goal is persisted in PGlite immediately, synced to cloud within 30 seconds online. |
| FR-001.2 | Agent generates a curriculum tree within 10 seconds of goal creation. | Must | Curriculum is a JSON tree of concepts with prerequisites and estimated depth. |
| FR-001.3 | Curriculum is editable by the learner before loop begins. | Should | Learner can add, remove, or reorder concepts. Changes are versioned. |
| FR-001.4 | Goals support metadata tags, estimated duration, and scheduling. | Should | Tags enable search/filter. Duration is used for progress reporting. |
| FR-001.5 | Recursion floor is a list of concept IDs the learner claims to know. | Should | Agent skips Feynman loops for floor concepts unless assessment indicates gaps. |

**UI Surfaces** (A2UI component types):
- `CreateGoalSurface`: Form with TextField (subject), ChoicePicker (proficiency), optional Markdown (context).
- `CurriculumTreeSurface`: Interactive tree with expandable nodes, drag-and-drop reordering (if editable).
- `GoalDashboardSurface`: Card grid of active/archived goals with progress bars.

### 3.2 Feynman Loop — Explain Phase (FEAT-002)

**Description**: The learner explains a concept in their own words, aided by the agent.

**User Stories**:
- US-002.1: As a learner, I can ask the agent to explain a concept to me so that I have a starting reference.
- US-002.2: As a learner, I can write my own explanation in a text area so that the Feynman loop can grade it.
- US-002.3: As a learner, I can see the agent's explanation outline before the full text so that I can steer the direction.
- US-002.4: As a learner, I can request analogies at different complexity levels (novice, peer, skeptic) so that I find what resonates.

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-002.1 | The agent generates an explanation outline (core idea + 2-3 analogies + anticipated challenges) before full text. | Must | Outline is rendered via A2UI `updateComponents` with approval buttons. |
| FR-002.2 | The learner can approve, request changes, or reject the outline. | Must | Rejection triggers a new outline generation. Changes are appended as constraints. |
| FR-002.3 | Full explanation is streamed via AG-UI text events as it is generated. | Must | Text appears character-by-character with < 100ms latency per chunk. |
| FR-002.4 | The explanation includes a "Teach the Skeptic" section when audience is peer or skeptic. | Must | Section addresses 2-3 anticipated objections with refutations. |
| FR-002.5 | The learner can save a draft explanation and resume later. | Should | Draft is auto-saved every 30 seconds to PGlite. |

**UI Surfaces**:
- `ExplainSurface`: Split-pane layout. Left: concept metadata. Right: streaming explanation with Markdown rendering.
- `OutlinePreviewSurface`: Card with bullet list, "Approve / Modify / Regenerate" buttons.
- `AnalogyCarouselSurface`: Horizontally swipeable cards for each analogy, each with a complexity badge.

### 3.3 Feynman Loop — Gap-Find Phase (FEAT-003)

**Description**: The agent grades the learner's explanation and identifies knowledge gaps.

**User Stories**:
- US-003.1: As a learner, I can submit my explanation for grading so that I know what I missed.
- US-003.2: As a learner, I can see a detailed rubric with scores for completeness, accuracy, clarity, and skeptic-handling. | Must | Rubric is a JSON object with per-criterion scores and comments. |
- US-003.3: As a learner, I can see a list of specific gap concepts that my explanation failed to cover correctly. | Must | Each gap has a severity (critical / major / minor) and a suggested remediation path. |
- US-003.4: As a learner, I can dispute a grade or gap identification so that the agent can refine its assessment. | Should | Dispute is logged and triggers a second-pass grading by a different model instance. |
- US-003.5: As a learner, I can solve transfer problems (novel applications) to demonstrate deep understanding. | Must | Two problems per concept, scored 0-1. Average must be ≥ 0.7 to pass. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-003.1 | Grading is performed by an LLM with sycophancy-correction to prevent false positives. | Must | "I feel like I understand this" never satisfies grading. |
| FR-003.2 | Grade output includes: overall_score (0-1), misconceptions_absent (0-1), gaps[], transfer_problems[]. | Must | Schema matches `Grade` entity in data model. |
| FR-003.3 | Gap concepts are automatically linked to the curriculum tree. | Must | If a gap is not in the curriculum, it is added as a child concept. |
| FR-003.4 | Transfer problems are novel — not rehearsed during the explanation phase. | Must | Each problem is generated fresh per grading attempt. |
| FR-003.5 | Grading results are persisted immediately and trigger AG-UI state_sync events. | Must | Frontend receives `state_sync` with `grading: "complete"` and full result payload. |

**UI Surfaces**:
- `GradeResultSurface`: Radial score chart, criterion breakdown table, expandable gap list.
- `TransferProblemSurface`: Interactive problem card with input fields, "Submit" button, and immediate feedback.
- `GapDrillSurface`: Tree view of gaps with "Study Now" buttons that spawn child Feynman loops.

### 3.4 Feynman Loop — Re-Study Phase (FEAT-004)

**Description**: The learner revisits gap concepts through targeted micro-sessions.

**User Stories**:
- US-004.1: As a learner, I can click a gap concept to start a focused Feynman loop on just that concept. | Must | Child loop inherits the same goal but runs at depth + 1. |
- US-004.2: As a learner, I can see my progress across all gap concepts in a dashboard. | Should | Progress is a kanban-style board: Pending → Explaining → Grading → Mastered. |
- US-004.3: As a learner, I can request alternative teaching modalities (video, interactive diagram, code example) for a gap concept. | Should | Agent generates a modality-specific A2UI surface. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-004.1 | Child loops are spawned automatically when gaps are identified and depth < 3. | Must | Child loop runs at depth + 1, audience resets to `novice`. |
| FR-004.2 | Recursion floor guards prevent infinite loops on foundational concepts. | Must | Floor concepts are skipped with a log entry. |
| FR-004.3 | After child loops complete, the parent explanation is re-executed with improved depth. | Must | Re-execution incorporates child loop explanations as references. |
| FR-004.4 | The learner can manually mark a gap as "not needed for my goal" to skip it. | Should | Skipped gaps are logged but do not block mastery. |

**UI Surfaces**:
- `GapBoardSurface`: Kanban board with columns, drag-and-drop cards, color-coded by severity.
- `ChildLoopSurface`: Miniaturized ExplainSurface with backlink to parent concept and depth indicator.

### 3.5 Feynman Loop — Mastery Closure (FEAT-005)

**Description**: The system determines when a concept is truly mastered and schedules retention.

**User Stories**:
- US-005.1: As a learner, I can see a mastery badge when all closure criteria are met. | Must | Badge is animated and shareable (optional). |
- US-005.2: As a learner, I receive a notification when a retention check is due (≥ 24h after mastery). | Must | Notification uses Tauri native notifications or web push. |
- US-005.3: As a learner, I can review all my mastered artifacts in a library. | Should | Library supports search, filter by goal, and export to PDF/Markdown. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-005.1 | Mastery requires all three criteria: grade ≥ 0.7, misconceptions_absent = 1.0, transfer average ≥ 0.7. | Must | Any single failure prevents mastery. |
| FR-005.2 | Retention is scheduled automatically at 24h, 7d, 30d, 90d intervals. | Must | Spaced repetition intervals are configurable per goal. |
| FR-005.3 | Retention checks are quick quizzes (1-2 questions) that must score ≥ 0.7 to pass. | Must | Failure triggers a re-study recommendation, not a full loop. |
| FR-005.4 | When all concepts in a goal are mastered, the learner is offered certification. | Should | Certificate is a generated PDF with goal title, completion date, and mastery scores. |

**UI Surfaces**:
- `MasteryBadgeSurface`: Animated SVG badge with concept name, score, and date.
- `RetentionQuizSurface`: Single-question card with timer, immediate feedback.
- `ArtifactLibrarySurface`: Searchable list with filter chips, export buttons, and preview panes.

### 3.6 AG-UI / A2UI Dynamic Surfaces (FEAT-006)

**Description**: The agent can render any UI surface dynamically, not just chat.

**User Stories**:
- US-006.1: As a learner, I can interact with forms generated by the agent (e.g., a concept mapping exercise). | Must | Form data is validated and submitted back to the agent. |
- US-006.2: As a learner, I can see charts and diagrams generated by the agent (e.g., a mind map of my knowledge). | Should | Charts are rendered via a charting component in the A2UI catalog. |
- US-006.3: As a learner, I can interact with the agent through buttons, sliders, and choice pickers embedded in the chat flow. | Must | Interactions emit AG-UI action events that the agent receives. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-006.1 | The frontend maintains a catalog of trusted A2UI component types. | Must | Catalog includes: Card, Column, Text, TextField, ChoicePicker, Button, Markdown, Chart, CodeBlock, Diagram. |
| FR-006.2 | All A2UI JSON is validated against a schema before rendering. | Must | Invalid JSON is rejected and a fallback message is shown. |
| FR-006.3 | Component actions (button clicks, form submits) emit AG-UI events back to the agent. | Must | Events include surfaceId, componentId, action name, and payload. |
| FR-006.4 | Surfaces can be created, updated, and destroyed dynamically by the agent. | Must | `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface` messages are all supported. |
| FR-006.5 | The agent can generate modality-specific surfaces based on the learning context. | Should | A CS concept may trigger a `CodeBlock` surface; a physics concept may trigger a `Diagram` surface. |

**UI Surfaces**:
- `SurfaceRenderer`: Generic A2UI renderer that maps JSON to React components.
- `ActionSurface`: Container for interactive elements that wire back to the AG-UI event bus.

### 3.7 MCP Tool Integration (FEAT-007)

**Description**: The agent can invoke external tools via the Model Context Protocol.

**User Stories**:
- US-007.1: As a learner, I can ask the agent to search the web for current information while learning. | Must | Agent requests web search via MCP, results are summarized and cited. |
- US-007.2: As a learner learning programming, I can have the agent execute code to verify my understanding. | Must | Code is executed in a sandboxed environment (e2b). Output is rendered in a CodeBlock. |
- US-007.3: As a learner, I can see which tools the agent is using and approve sensitive ones. | Must | Tool calls are rendered as cards with status (pending / running / complete / error). |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-007.1 | The Axum server acts as an MCP client connecting to configured servers. | Must | Supported transports: stdio, HTTP, SSE. |
| FR-007.2 | Tool calls are surfaced to the learner via AG-UI `tool_call` and `tool_result` events. | Must | Cards show tool name, arguments, progress spinner, and result. |
| FR-007.3 | Destructive or expensive tools require explicit user approval before execution. | Must | Approval dialog is an A2UI surface with "Approve / Deny" buttons. |
| FR-007.4 | Tool results are cached for 5 minutes to avoid redundant calls. | Should | Cache key is hash of tool name + arguments. |
| FR-007.5 | MCP server configuration is hot-reloadable via ArcSwap. | Should | New servers can be added without restarting the Axum server. |

**Supported MCP Tools (initial set)**:
| Tool | Server | Use Case |
|---|---|---|
| `web_search` | Brave/Perplexity MCP | Real-time knowledge retrieval. |
| `code_execute` | e2b MCP | Sandbox code execution for CS learning. |
| `calculator` | Built-in | Mathematical verification. |
| `diagram_generate` | Mermaid/Kroki MCP | Generate visual diagrams for explanations. |
| `file_read` | Local FS MCP | Read uploaded documents for context. |
| `knowledge_query` | Supabase/vector MCP | RAG over the learner's past artifacts. |

### 3.8 Offline-First & Sync (FEAT-008)

**Description**: The app works fully offline, with transparent sync when online.

**User Stories**:
- US-008.1: As a learner, I can create goals and write explanations while offline. | Must | All writes go to local PGlite. No error is shown. |
- US-008.2: As a learner, I can see which data is pending sync with a visual indicator. | Should | Indicator shows queue length and estimated sync time. |
- US-008.3: As a learner, my data is automatically synced when I come back online. | Must | Sync is incremental and resumes from interruption. |
- US-008.4: As a learner, I can force a manual sync at any time. | Should | Pull-to-refresh gesture or manual button. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-008.1 | PGlite is initialized with the full schema on first launch. | Must | Schema is downloaded from the server or bundled with the app. |
| FR-008.2 | ElectricSQL shapes define what data syncs per-learner. | Must | Shapes: goals, concepts, artifacts, grades, retention_checks. |
| FR-008.3 | Sync conflicts use last-write-wins with per-column resolution for critical fields. | Must | `mastery_score`, `status`, and `explanation_text` are treated as user-wins. |
| FR-008.4 | Offline indicator is shown when the client detects network loss. | Must | Indicator is a subtle banner, not a blocking modal. |
| FR-008.5 | Full sync of a new device takes < 60 seconds for a learner with 100 goals and 1000 artifacts. | Should | Benchmarked on a 10Mbps connection. |

### 3.9 Karpathy Loop — Continuous Improvement (FEAT-009)

**Description**: The system autonomously improves its teaching based on learner outcomes.

**User Stories**:
- US-009.1: As a platform admin, I can see an experiment dashboard showing which pedagogical changes improved learner outcomes. | Should | Dashboard shows experiment list, LVS delta, and confidence intervals. |
- US-009.2: As a platform admin, I can approve or reject proposed curriculum changes from the Improvement Agent. | Should | Changes are presented as diffs with rationale. |

**Functional Requirements**:

| ID | Requirement | Priority | Acceptance Criteria |
|---|---|---|---|
| FR-009.1 | The Quarry reflection engine (`fdb-reflection`) computes Learning Velocity Score (LVS) per cohort. | Must | LVS = (mastery_rate × 0.4) + (1 / avg_recursion_depth × 0.3) + (retention_pass_rate × 0.3). |
| FR-009.2 | The Improvement Agent proposes experiments: e.g., "try analogy type X for cohort Y". | Must | Proposals include hypothesis, expected LVS delta, and risk assessment. |
| FR-009.3 | Experiments run for a fixed 24-hour window on a randomized subset of learners. | Must | Control group is maintained. Randomization is stratified by proficiency level. |
| FR-009.4 | Winning experiments (p < 0.05, LVS improvement > 5%) are auto-committed to the curriculum. | Should | Commit requires human approval if > 20% of curriculum is affected. |
| FR-009.5 | All experiments are logged immutably with git-style history. | Must | `experiment_log` table stores hypothesis, parameters, results, and commit SHA. |

## 4. Data Contracts & API Specification

### 4.1 Feynman Loop API

#### POST /api/v1/learn/feynman-loop

**Request**:
```json
{
  "concept_id": "uuid",
  "goal_id": "uuid",
  "depth": 0,
  "audience": "novice",
  "explanation_text": "optional user draft"
}
```

**Response** (streamed via AG-UI SSE):
```json
{
  "type": "ag_ui_event",
  "event": {
    "kind": "text",
    "content": "The core idea of quantum entanglement is..."
  }
}
```

#### POST /api/v1/learn/grade

**Request**:
```json
{
  "artifact_id": "uuid",
  "explanation_text": "user's full explanation",
  "transfer_answers": ["answer 1", "answer 2"]
}
```

**Response**:
```json
{
  "grade_id": "uuid",
  "overall_score": 0.82,
  "misconceptions_absent": 1.0,
  "gaps": [
    {
      "concept_id": "uuid",
      "title": "Bell's Inequality",
      "severity": "major",
      "remediation_path": "Study Bell's Inequality before re-explaining entanglement."
    }
  ],
  "transfer_problems": [
    {
      "problem": "Alice and Bob share an entangled pair...",
      "expected_answer": "...",
      "user_answer": "...",
      "score": 0.85
    }
  ],
  "mastered": false
}
```

## 5. State Machines

### 5.1 Concept Lifecycle State Machine

```
[Pending] --(user starts explain)--> [Explaining]
[Explaining] --(user submits explanation)--> [Grading]
[Grading] --(gaps found, depth < 3)--> [Gaps] --(child loops started)--> [Explaining] (child)
[Grading] --(gaps found, depth >= 3)--> [Gaps] --(gaps noted for review)--> [Pending] (parent re-explain)
[Grading] --(no gaps, transfer < 0.7)--> [Explaining] (transfer practice)
[Grading] --(no gaps, transfer >= 0.7)--> [Mastered] --(24h)--> [Retention Due]
[Retention Due] --(quiz passed)--> [Mastered]
[Retention Due] --(quiz failed)--> [Explaining] (re-study)
```

### 5.2 Sync State Machine (per shape)

```
[Unsynced] --(online + shape subscription)--> [Subscribing]
[Subscribing] --(shape confirmed)--> [Live]
[Live] --(network loss)--> [Paused] --(network restored)--> [Resuming]
[Resuming] --(catch-up complete)--> [Live]
[Live] --(local write)--> [Local Dirty] --(sync push)--> [Live]
```

## 6. Error Handling & Edge Cases

| Scenario | Behavior | Fallback |
|---|---|---|
| LLM API unavailable | Retry with exponential backoff (max 3). Fall back to local LLM if configured. | Show offline-mode message with cached explanations. |
| MCP server timeout | Mark tool call as failed. Surface error to user. Allow retry. | Suggest alternative tool or manual approach. |
| Sync conflict (LWW ambiguous) | Prompt user to choose which version to keep. | Both versions are stored; admin can merge later. |
| PGlite initialization failure | Fall back to in-memory mode. Warn user that data is ephemeral. | Allow manual export before browser close. |
| Grading service overload | Queue grading job. Show "grading in progress" spinner. | Async notification when grading completes. |
| Subscription webhook failure | Retry webhook delivery. Grace period of 24h before downgrade. | Email user with manual renewal link. |
| Tauri IPC failure | Fallback to HTTP loopback (if Axum server is running). | Show error and recommend app restart. |

| Requirement | Approach |
|---|---|

## 8. Glossary

| Term | Definition |
|---|---|
| **A2UI** | Agent-to-User Interface — Google's declarative JSON protocol for AI-generated UI. |
| **AG-UI** | Agent-User Interaction — CopilotKit's event streaming protocol for agent-frontend communication. |
| **ArcSwap** | Lock-free Rust primitive for hot-swapping shared state (e.g., config, router). |
| **Feynman Loop** | The four-phase learning cycle: Explain → Gap-Find → Re-Study → Mastery. |
| **Karpathy Loop** | Andrej Karpathy's autonomous experiment loop: editable asset, scalar metric, time-boxed cycle. |
| **LVS** | Learning Velocity Score — composite metric for measuring pedagogical effectiveness. |
| **MCP** | Model Context Protocol — Anthropic's open standard for connecting AI agents to external tools. |
