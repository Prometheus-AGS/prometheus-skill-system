# kbd-no-silent-journal-fork

## Why

Observed (2026-11-10, reproduced while diagnosing `kbd-team-device-enrollment`): a teammate
clones a repository whose KBD plan was written by another machine's signed journal. The
teammate's machine has no local copy of that journal. Their first KBD write calls
`ensure_runtime`, which finds no events and silently signs a brand-new genesis event with the
teammate's key. The teammate becomes the sole operator of a second journal for the same
`projectId`, and the shared plan splits in two without any warning.

The checked-in `.kbd-orchestrator/current-waypoint.json` already records that a journal exists:
the runtime writes it with `generatedBy: "kbd-runtime"` and `sourceRevision > 0`. Waypoints from
pre-runtime (legacy) projects have no `generatedBy` field.

## What changes

- CLI `ensure_runtime` (the only path that signs a new genesis: first typed mutation and
  `kbd migrate --apply`) refuses when the local journal is empty and the checked-in waypoint was
  generated by `kbd-runtime` at a revision above 0. The error names the project, run and revision,
  says the journal lives on another machine, and points to syncing or restoring it.
- `PROMETHEUS_KBD_NEW_JOURNAL=1` lets an operator deliberately start a new journal when the
  original is permanently lost.
- Brand-new projects and legacy (pre-runtime) projects still bootstrap as before.

## Out of scope

- Journal transport between machines (sovereign-sync / control plane) is unchanged.
- Repairing journals that were already forked.
