# PyO3 Rust-Python Bridge

## Use Case in Prometheus AGS

PyO3 bridges are used in two contexts:

1. **Skill executor code generation** — forge-rs generates Python scripts that call
   into Rust crates via PyO3 bindings. These scripts become executable tool code
   in Dify knowledge base workflows, Claude Code slash commands, and MCP skill servers.

2. **Python MCP tool servers** — skill executor servers in Python that expose Rust
   capabilities (inference, memory, policy evaluation) without requiring the caller
   to build Rust.

## Exposing Rust Functions

```rust
// src/lib.rs
use pyo3::prelude::*;

/// A function exposed to Python.
/// The docstring becomes the Python __doc__.
#[pyfunction]
fn enrich_task(task_path: &str, language: &str) -> PyResult<String> {
    // Call into Rust logic — no async here (sync bridge)
    let lang = language.parse::<forge_core::Language>()
        .map_err(|e| PyErr::new::<pyo3::exceptions::PyValueError, _>(e.to_string()))?;

    // For now, return a placeholder — real impl would call forge-enricher
    Ok(format!("Enriched {} for {}", task_path, lang.as_str()))
}

/// Exposing a Rust struct as a Python class.
#[pyclass]
struct SkillInfo {
    #[pyo3(get)]
    pub name: String,
    #[pyo3(get)]
    pub language: String,
}

#[pymethods]
impl SkillInfo {
    #[new]
    fn new(name: String, language: String) -> Self {
        Self { name, language }
    }

    fn __repr__(&self) -> String {
        format!("SkillInfo(name={:?}, language={:?})", self.name, self.language)
    }
}

/// The Python module definition.
#[pymodule]
fn my_python_bridge(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(enrich_task, m)?)?;
    m.add_class::<SkillInfo>()?;
    Ok(())
}
```

## GIL Management

PyO3 acquires the GIL when Rust calls into Python. For long-running Rust operations,
release the GIL to allow other Python threads to run:

```rust
#[pyfunction]
fn heavy_computation(py: Python<'_>, data: Vec<f32>) -> PyResult<Vec<f32>> {
    // Release GIL during the heavy work
    py.allow_threads(|| {
        // This block runs without the GIL
        data.iter().map(|x| x * 2.0).collect::<Vec<_>>()
    });
    // GIL re-acquired here
    Ok(result)
}
```

## Async Bridge (pyo3-asyncio)

For exposing async Rust functions to Python's `asyncio`:

```toml
[dependencies]
pyo3-asyncio = { version = "0.21", features = ["tokio-runtime"] }
```

```rust
use pyo3_asyncio::tokio::future_into_py;

#[pyfunction]
fn async_enrich<'py>(py: Python<'py>, task_path: String) -> PyResult<Bound<'py, PyAny>> {
    future_into_py(py, async move {
        let result = forge_enricher::enrich_task_simple(&task_path)
            .await
            .map_err(|e| PyErr::new::<pyo3::exceptions::PyRuntimeError, _>(e.to_string()))?;
        Ok(result)
    })
}
```

## Generated Skill Executor Pattern

When forge-rs generates Python executor code for a skill, it produces this pattern:

```python
# Generated by forge-rs — do not edit manually
# forge:skill=rust/performance, forge:task=CHANGE-042

import my_python_bridge as forge

def execute_skill(task_path: str, language: str = "rust") -> dict:
    """Execute the forge enrichment for this task."""
    context = forge.enrich_task(task_path, language)
    return {
        "context": context,
        "skill": "rust/performance",
        "status": "enriched",
    }

if __name__ == "__main__":
    import json, sys
    result = execute_skill(sys.argv[1])
    print(json.dumps(result))
```

This script is the "executor" registered with a skill server. It can be called
from Dify workflows, MCP tool servers, or Claude Code slash commands without
requiring the caller to understand Rust.

## Forbidden Patterns

- `import *` — explicit imports only
- `except:` without exception type — always `except SomeError:`
- Storing Python objects (`Py<T>`) across threads without proper GIL management
- Calling Python callbacks from Rust threads without acquiring the GIL first
- Using `pyo3::Python::with_gil()` inside a `py.allow_threads()` block — deadlock
- Skipping `maturin develop` before testing — the `.so` must be recompiled after Rust changes
